# Agentic, Secure, Efficient Desktop Browsing: Agent Layer and Security Practices for Bucks Browser (as of 2026-10-19)

Scope note: ~25 tool calls of research. Questions 1 (protocols) and 2 (security) are well sourced from primary docs. Frameworks (OpenAI Agents SDK, LangGraph, ADK, smolagents, Claude Agent SDK), AGNTCY, libp2p pubsub, Electron-browser peers (Min/Beaker/Wavebox), DoH, passkeys, tab discarding and productivity-feature evidence were NOT researched in this pass; they are listed under Gaps rather than asserted.

## 1. Agent protocols and frameworks (MCP, A2A, others) and what to build on

### Takeaway
MCP is the de-facto tool-registry protocol and its 2026-07-28 revision (final, stateless) fits a local sidecar well; A2A reached v1.0 in March 2026 under the Linux Foundation and is the reference for agent-to-agent, but is HTTP/gRPC-centric, so a libp2p transport would be a custom binding. Framework comparison could not be completed with sources.

### Cited Findings
- MCP spec revision 2026-07-28 supersedes 2025-11-25. Major changes: protocol-level sessions and `Mcp-Session-Id` removed from Streamable HTTP; the `initialize` handshake removed (every request carries protocol version and client capabilities in `_meta`); new mandatory `server/discover` RPC; `subscriptions/listen` replaces the GET endpoint; SSE stream resumability removed — [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/latest/changelog)
- Same revision: tasks moved to an official extension (`io.modelcontextprotocol/tasks`); "Multi Round-Trip Requests" (`input_required` results) replace server-initiated `sampling/createMessage`, `elicitation/create`, `roots/list`; Roots, Sampling and Logging features deprecated (12-month minimum deprecation window); HTTP+SSE transport formally Deprecated; `tools/list` results now carry `ttlMs`/`cacheScope` and servers SHOULD return tools in deterministic order (helps LLM prompt-cache hits); OpenTelemetry trace context in `_meta` — [MCP changelog](https://modelcontextprotocol.io/specification/latest/changelog)
- MCP authorization is OPTIONAL; HTTP transports SHOULD follow the spec, STDIO SHOULD NOT (read credentials from environment). Based on OAuth 2.1 draft; servers MUST implement RFC 9728 Protected Resource Metadata; clients MUST send RFC 8707 `resource` parameter in authorization and token requests; PKCE flow; tokens never in query string; servers MUST validate audience and MUST NOT accept/transit other tokens; clients MUST validate `iss` (RFC 9207) before redeeming codes — [MCP Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Client registration: Client ID Metadata Documents (HTTPS URL as client_id) are the SHOULD-support mechanism; Dynamic Client Registration (RFC 7591) is deprecated but retained; clients MUST key persisted credentials by issuer — [MCP changelog](https://modelcontextprotocol.io/specification/latest/changelog); [MCP Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Scope handling: least privilege, progressive step-up via `WWW-Authenticate scope=`, `insufficient_scope` 403, bounded retries — [MCP Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- MCP security best-practices page covers: confused deputy in OAuth proxies (per-client consent required), token passthrough (forbidden), SSRF in OAuth discovery (block private/link-local ranges, validate redirects, pin DNS), state-handle hijacking, local MCP server compromise (show exact command before one-click install, sandbox, prefer stdio or restricted unix sockets / auth tokens for local HTTP), OAuth URL validation (allow only http/https; never open URLs through a shell), stdio-proxy privilege escalation, mix-up attacks, localhost redirect impersonation, scope minimization — [MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)
- A2A: first stable v1.0 in March 2026 (one guide gives 12 March; another source says April, treated as less reliable); hosted by the Linux Foundation, >150 supporting organisations per its 9 April 2026 press release; v1.0 added multi-protocol bindings (JSON-RPC, gRPC, HTTP+JSON per a secondary guide), multi-tenancy, Signed Agent Cards (cryptographic identity), migration path; Microsoft (Azure AI Foundry, Copilot Studio) and AWS (Bedrock AgentCore Runtime) added support — [Linux Foundation press release](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year); [Google Open Source Blog, Apr 2026](https://opensource.googleblog.com/2026/04/a-year-of-open-collaboration-celebrating-the-anniversary-of-a2a.html); [chatforest guide (secondary)](https://chatforest.com/guides/a2a-protocol-v1-production-ready/)
- Playwright MCP: Apache-2.0, Microsoft-maintained; npm @playwright/mcp v0.0.76 as of June 2026; one benchmark reports ~114k tokens for a task via MCP vs ~27k via the Playwright CLI (secondary, vendor-blog) — [morphllm.com summary](https://www.morphllm.com/playwright-mcp)
- Stagehand: MIT, TypeScript-first, v3 caches successful actions to avoid repeat LLM calls (secondary roundup) — [respan.ai comparison](https://www.respan.ai/market-map/compare/playwright-vs-stagehand); [morphllm Stagehand MCP](https://www.morphllm.com/stagehand-mcp)
- Browser Use: roundups cite ~81k GitHub stars and a CLI 3.0 on 1 July 2026; licence not confirmed by search — [awesomeagents.ai comparison](https://awesomeagents.ai/tools/best-ai-browser-automation-tools-2026/)
- Project state (read-only inspection): Soul Engine has a `Tool` class with a `safe` flag ("False = requires user confirmation"), a planner module, a browser-action approve/cancel gate (`POST /agent/approve/{session_id}`, 30 s timeout), a pending-update quarantine for peer-supplied knowledge/skill updates needing explicit approval, an `mcp_server.py`, a `p2p/` package, and regex-based `safety.py` (harm/bias keyword patterns, card-number output filter, rate limiter). `safety.py` has no prompt-injection or exfiltration logic — local files `agent/tools/registry.py`, `agent/safety.py`, `agent/soul_engine.py`.

### Inferences
- Tool registry: keep the in-process registry but expose it as an MCP server (already partly present in `mcp_server.py`) and consume third-party servers only via a gateway in the Electron main process that enforces consent, sandboxing and OAuth (the MCP spec itself pushes clients to own this). Target 2026-07-28 semantics (stateless, `server/discover`); avoid Sampling/Roots/legacy SSE since they are deprecated.
- Per-tool permission model: extend the binary `safe` flag into capability classes (read-page, read-private-store, write-local, network-egress, state-changing-web-action, spend/send) with per-origin and per-session grants, mirroring MCP scope step-up (least privilege, escalate on demand).
- Planner/executor split: a trusted planner sees only the user request and sanitized structured data; a quarantined reader model (can be the same local model with no tools) processes page content — see Question 2 (CaMeL / dual-LLM / Chrome's Critic).
- Peer communication: A2A's Agent Card + signed-card idea maps naturally to a card pinned in IPFS and signed with the Soul's key; libp2p pubsub would carry A2A JSON-RPC messages as a custom transport binding (not an existing A2A binding as far as sources show). Treat all peer messages as untrusted input (the existing pending-update quarantine is the right pattern).
- On-device and cloud-free: MCP and A2A are protocols, not runtimes, so both are compatible with local-first; framework choice should be driven by licence (MIT/Apache) and ability to run against llama.cpp's OpenAI-compatible endpoint (not verified here).

### Gaps
- No sourced comparison for OpenAI Agents SDK, Claude Agent SDK, LangGraph, Google ADK, smolagents (versions, licences, local-model fit): not researched in this pass.
- AGNTCY / agent identity efforts: not researched.
- libp2p/IPFS pubsub as an A2A transport: no sources found or searched; any recommendation is design inference only.
- Browser Use licence unconfirmed from sources (commonly reported as MIT; verify in its repo).
- Primary A2A spec text (a2a-protocol.org) not fetched; v1.0 details rely on press release and secondary guides.

## 2. Browser-agent security: threats, incidents, published defences, design patterns

### Takeaway
Indirect prompt injection is accepted by vendors as not fully solvable; the credible defences are architectural (isolate untrusted content from the planner, restrict origins, gate state-changing actions, separate agent session, independent critic) layered with classifiers and red-teaming. Regex guardrails of the kind in `safety.py` are not a defence against this class.

### Cited Findings
- Brave (Aug 2025) disclosed indirect prompt injection in Perplexity Comet (hidden white-on-white text, HTML comments, near-invisible image text). Follow-up 21 Oct 2025: "unseeable" injections in screenshots (faint text OCR'd and passed to the LLM; reported to Perplexity 1 Oct 2025), and Fellou, where merely navigating to an attacker page triggered injection (reported 20 Aug 2025); an Opera Neon flaw was disclosed 31 Oct 2025. Brave's stated recommendation: isolate agentic browsing from regular browsing and start agentic actions only on explicit user invocation — [Brave blog](https://brave.com/blog/unseeable-prompt-injections/); [Simon Willison summary](https://simonwillison.net/2025/Oct/21/unseeable-prompt-injections/)
- OpenAI (22 Dec 2025): continuous hardening of ChatGPT Atlas with an RL-trained automated attacker and adversarially trained model; OpenAI concedes prompt injection is unlikely to ever be fully "solved"; user-facing advice: limit access, require confirmation for messages/payments, avoid vague "do whatever is needed" prompts — [OpenAI](https://openai.com/index/hardening-atlas-against-prompt-injection); [TechCrunch](https://techcrunch.com/2025/12/22/openai-says-ai-browsers-may-always-be-vulnerable-to-prompt-injection-attacks/); critique: [Zenity Labs](https://labs.zenity.io/p/hardening-atlas-the-relentless-challenge-of-securing-an-untrusted-browser-agent)
- Google Chrome (Nathan Parker, 8 Dec 2025): (1) User Alignment Critic — a separate model, isolated from untrusted content, sees only action metadata and vetoes actions not serving the user's goal, run after planning and before execution; inspired by dual-LLM and CaMeL; (2) Agent Origin Sets — per-session read-only and read-writable origin sets, with a trusted gating function (not influenced by page content) approving new origins; model-generated URLs checked deterministically against known public URLs; (3) confirmations for sensitive sites (banking, medical), sign-in via Password Manager (model never sees passwords), purchases, payments, messaging; (4) a parallel prompt-injection classifier; (5) automated red-teaming; bounties up to $20,000 for boundary breaks — [Google Chrome security blog](https://blog.google/security/architecting-security-for-agentic/)
- Anthropic Claude for Chrome pilot (Aug 2025): 123 adversarial cases / 29 scenarios; unmitigated attack success 23.6%, 11.2% with mitigations in autonomous mode (Anthropic figures; Simon Willison called 11.2% "catastrophic"); defences: site-level permissions, confirmation before high-risk actions, blocked categories by default, injection classifiers. A later claim of 0–0.3% is from a secondary summary and unverified — [Anthropic](https://www.anthropic.com/news/claude-for-chrome); [Simon Willison](https://feeds.simonwillison.net/2025/Aug/26/piloting-claude-for-chrome); [AI Magazine (secondary)](https://aiunderstanding.org/news/anthropic-makes-claude-in-chrome-generally-available-with-autonomous-browser-actio)
- 2026 incidents (Cloud Security Alliance research notes, secondary write-ups of vendor research; no CVE ids found): Zenity "PleaseFix"/PerplexedBrowser (3–4 March 2026) zero-click agent hijack of Comet giving local file access and credential theft; LayerX "BioShocking" (24 June 2026) compromised six AI browsers/extensions from OpenAI, Anthropic and Perplexity via a game-themed page, with reportedly only Atlas fixed effectively; CSA groups related named attacks (ZombieAgent, GeminiJack, Tainted Memories, HashJack, CometJacking) — [CSA PleaseFix](https://labs.cloudsecurityalliance.org/research/csa-research-note-pleasefix-agentic-browser-exploits-2026032/); [CSA BioShocking](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-browser-prompt-injection-20260630-csa-s/); [Help Net Security](https://helpnetsecurity.com/2026/03/04/agentic-browser-vulnerability-perplexedbrowser)
- OWASP Top 10 for Agentic Applications 2026 (published 9 Dec 2025, per secondary summaries): ASI01 Agent Goal Hijack, ASI02 Tool Misuse & Exploitation, ASI03 Identity & Privilege Abuse, ASI04 Agentic Supply Chain, ASI05 Unexpected Code Execution, ASI06 Memory & Context Poisoning, ASI07 Insecure Inter-Agent Communication, ASI08 Cascading Failures, ASI09 Human-Agent Trust Exploitation, ASI10 Rogue Agents — [Cycode summary](https://cycode.com/blog/owasp-top-10-agentic-applications/) (OWASP primary not fetched)
- Lethal trifecta (Simon Willison, 16 June 2025): private data + untrusted content + external communication in one agent; only reliable mitigation is to avoid the combination; guardrail products claiming ~95% are insufficient — [Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- CaMeL (Google DeepMind et al., arXiv 2503.18813): extracts control and data flow from the trusted user query so untrusted data cannot change program flow; capabilities restrict data flows at tool calls; solves 77% of AgentDojo tasks with provable security vs 84% undefended (current version; earlier version said 67%); authors say it does not address every attack vector; code at google-research/camel-prompt-injection — [arXiv](https://arxiv.org/abs/2503.18813)
- "Design Patterns for Securing LLM Agents against Prompt Injections" (14 authors incl. Beurer-Kellner, Tramèr, Paverd; v1 10 June 2025, v3 27 June 2025) proposes principled patterns; Willison counts six; the abstract page did not list them — [arXiv 2506.08837](https://arxiv.org/abs/2506.08837)
- MCP-specific: one-click local server installs must show the exact command and sandbox servers; reject non-http(s) URL schemes and never open URLs through a shell — [MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)

### Inferences
- Concrete pattern set for Bucks (all derived from the sources above): (a) separate agent profile/session partition with no access to the user's logged-in cookies unless a per-site grant is given (Brave, Chrome Origin Sets); (b) trusted gate in the Electron main process owning the origin read/write sets, not the Python sidecar's LLM; (c) planner never reads raw page text — a quarantined extractor returns typed fields (CaMeL/dual-LLM); (d) deterministic, non-LLM check that any URL/image/link the agent emits or renders is on the allowed set, and disable remote images and auto-links in rendered markdown/generative-UI cards from untrusted-derived text (exfiltration channel from the trifecta; generic principle, specific markdown-image incidents not sourced here); (e) human approval for state-changing, spending, sending and credential actions, with the approval UI rendered by the trusted shell showing the real target origin and arguments; (f) tamper-evident action log and per-tool rate limits; (g) wrap page content in explicit untrusted delimiters (spotlighting — technique not sourced in this pass) as defence in depth only.
- The 30 s approval timeout in `_await_approval` should default to deny (verify in code); `safety.py` regex filters should be reframed as content-policy only, not security.
- Local-model caveat: small local models are likely easier to hijack than frontier models (no source; hypothesis), reinforcing the need for architectural, not model-based, controls.

- Six design patterns from the Beurer-Kellner et al. paper not enumerated; spotlighting (Microsoft) and AgentDojo numbers not fetched.

## 3. Local models for on-device inference (2026)

### Takeaway
Qwen-family models at ~8B+ are the most consistently reported reliable small tool-callers; below ~4B tool calling degrades sharply; Gemma 4 offers good memory footprints but weaker agentic reports. Evidence is mostly secondary/anecdotal, so Bucks should run its own evals on its own tool schemas.

### Cited Findings
- Google's Gemma 4 memory table at 4-bit (incl. ~20% load overhead, excluding context): E2B ~2.9 GB, E4B ~4.5 GB, 12B ~6.7 GB, 26B-A4B ~14.4 GB, 31B ~17.5 GB — [Google AI for Developers](https://ai.google.dev/gemma/docs/core)
- Single-user anecdote: Gemma 4 26B MoE ~15 tok/s on a 16 GB RAM + RTX 3050 laptop via ik_llama.cpp (~10 tok/s at 8k context); E4B 30–40 tok/s; judged weak on agentic tasks — [community post](https://activitypub.space/topic/53635cf8-4e9e-4dfe-ae2b-287eb740c95b/i-ran-gemma-26b-on-4gb-vram-16ram.-15-t-s-on-avarage) (anecdotal)
- Docker evaluation (2025): Qwen 3 14B tool-selection F1 0.971 (near GPT-4), Qwen3 8B Q4_K_M 0.919, gemma3 4B 0.733 — [Docker blog](https://www.docker.com/blog/local-llm-tool-calling-a-practical-evaluation/)
- A July 2026 guide reports BFCL-v4 for Qwen3.5 dense: 27B 0.685, 9B 0.661, 4B 0.503, 2B 0.436, and that reliability falls off below ~4B; notes models with trained-in tool templates (Qwen) beat those needing grammar-constrained decoding (Gemma 2/3). Unverified against the official leaderboard — [d-central.tech](https://d-central.tech/local-llm-agent-capability/)
- Claims that MLX beats llama.cpp Metal for models under ~14B come from a secondary guide — [promptquorum / toolradar-type guides](https://www.promptquorum.com/power-local-llm/best-local-models-tool-calling-2026) (unverified)

### Inferences
- For an 8–16 GB laptop: a 4–9B Q4 model (~3–6 GB) plus KV cache leaves room for the browser; use grammar/JSON-schema-constrained decoding for tool calls in llama.cpp and keep the toolset small per turn (the project's `select_tool_schemas` already narrows tools).
- Cloud fallback should be opt-in per task, with local redaction and a visible indicator; the trusted planner/gate must stay local even when the executor is remote.

### Gaps
- No primary benchmark for llama.cpp tool-calling per model/quant; no MLX, ONNX/WebGPU, Phi or Llama 2026 numbers; Qwen3.5 memory/latency not found. Ollama vs llama.cpp comparison not sourced.

## 4. Daily-driver Electron browser security and efficiency

### Takeaway
Electron's official 20-item checklist is the baseline; Electron supports only the latest three majors with ~8-week cadence, so patch discipline is the main residual risk. Extension support is deliberately limited, so use library-level blocking (Ghostery).

### Cited Findings
- Electron security checklist (official): HTTPS only; no Node integration for remote content; contextIsolation on; sandbox all renderers; `setPermissionRequestHandler` (Electron approves all requests by default); don't disable `webSecurity`; restrictive CSP; no `allowRunningInsecureContent`; no experimental/Blink flags; no `allowpopups`; verify webview options via `will-attach-webview`; limit navigation with `will-navigate` parsed by URL parser; `setWindowOpenHandler`; never pass untrusted input to `shell.openExternal`; keep Electron current; validate IPC sender frame origin; avoid `file://` (use `protocol.handle`); flip fuses with `@electron/fuses` (disable `runAsNode`, `nodeCliInspect`); don't expose raw Electron APIs through contextBridge — [Electron security docs](https://www.electronjs.org/docs/latest/tutorial/security)
- Support policy: latest 3 stable majors, only newest minor of each; new major about every 8 weeks tied to Chrome stable; Chromium bumped usually 1–2 weeks after Chrome stable. Per a third-party page dated 6 Oct 2026: Electron 42 (Chromium M148) EOL 20 Oct 2026, Electron 43 supported to 5 Jan 2027, Electron 44 to 2 Mar 2027, Electron 45 stable on 20 Oct 2026 — [Electron timelines](https://electronjs.org/docs/latest/tutorial/electron-timelines); [endoflife.date/electron](https://endoflife.date/electron)
- Electron extension support: a subset of Chrome Extensions API mainly for DevTools; arbitrary store extensions not supported (explicit non-goal); unpacked only (no .crx), per persistent session, reloaded every launch — [Electron extensions docs](https://Electronjs.org/docs/latest/api/extensions)
- `@ghostery/adblocker-electron` exists as a library integration for Electron (filter lists compatible with uBlock/EasyList) — [ghostery/adblocker](https://github.com/ghostery/adblocker)
- MCP-client hardening that applies to a browser: block private/link-local/loopback targets when fetching agent- or server-supplied URLs, no shell-based URL opening — [MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)

### Inferences
- Bucks, on Electron 44, will need to move to 45 and then 46 in step with the 8-week cadence; Electron 44 support ends 2 Mar 2027 per the third-party schedule. Build automated update and a rapid-release path since the agent adds a larger attack surface.
- WebContentsView tab content should run with sandbox on, contextIsolation on, no preload exposure beyond a minimal validated API, per-agent-session partition, and a permission handler default-deny; chrome UI (including generative-UI cards) lives in a separate trusted view with strict CSP and no remote content.

### Gaps
- Not researched: site isolation specifics in Electron, cookie partitioning, DoH config, HTTPS-first, WebAuthn/passkeys in Electron, fingerprinting resistance, memory/CPU tab discarding, what Min/Beaker/Wavebox/Arc do, update-strategy best practice, whether `webRequest` is a viable path for adblocking in current Electron.

## 5. Productivity features users value, and which are low risk

### Takeaway
Not evidenced in this pass.

### Cited Findings
- Vendor guidance converges on confirmation before sends/payments/purchases and on limiting what the agent can access, which implicitly classes read-only features (summarise current page, local history search) as lower risk than form-fill or messaging — [OpenAI](https://openai.com/index/hardening-atlas-against-prompt-injection); [Google Chrome security blog](https://blog.google/security/architecting-security-for-agentic/)

### Inferences
- Lowest risk: summarisation and local semantic search over history using a tool-less model whose output is plain text with no links/images; medium: research mode (reads many untrusted pages but no private data — keep it in the isolated profile); high: form fill, cross-site actions, email/messaging, purchases (approval gates required). This ranking is derived from the lethal-trifecta framing, not from usage evidence.

### Gaps
- No usage or survey evidence on which agentic-browser features users value (Comet, Atlas, Dia, Edge Copilot, Opera Neon); not researched.
