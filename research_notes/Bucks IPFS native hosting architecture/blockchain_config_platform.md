## Q1. What is the Bucks chain code in `buckscore` today, and does it run?

### Takeaway
The Go `node/` is a roughly 2.2k-line scaffold (not a working chain): it has a PoW header check, a LevelDB block store and a libp2p skeleton, but no state trie, no EVM, no transactions or mempool, a placeholder header hash, and stubbed JSON-RPC balance/nonce/send methods. The architecture docs describe an EVM chain with `state/` and `evm/` packages that do not exist in the repo. A separate, much larger C++ UTXO chain (not in this clone) is the more complete chain engine but has no smart contracts.

### Cited Findings

**Chain type, consensus, parameters (documented vs coded)**
- Docs claim a "sovereign, EVM-compatible" PoW chain, chain ID 8192, 60 s blocks, 50 BUCKS reward halving every 210,000 blocks, 21M cap, double-Keccak-256 PoW, EVM Berlin baseline, with `core/state/statedb.go` and `core/evm/evm.go` packages — `bucks-blockchain-architecture.md` (sections 3.2 and 3.3).
- The repo has no `state/` or `evm/` package. `node/` contains only `cmd/bucksnode`, `core/{types,blockchain,consensus,p2p}`, `api`, `config` (9 Go files plus api and config; about 2,240 lines in node, per `PROJECT_MAP.md` section 3, which itself calls it "thin/skeletal").
- Constants: ChainID 8192, reward 50, HalvingInterval 210,000, MaxSupply 21M, TargetBlockTime 60 s, DifficultyAdjustmentWindow 2016 — `node/core/types/block.go:17-47`. The supply arithmetic (50 x 210,000 x 2 = 21M) is consistent with `PROJECT_MAP.md` lines 55-66 (which also record that a "114,000,000" supply figure in `bucks-contracts-plan.md` was an error and was corrected).
- Fees/gas: `eth_gasPrice` returns a constant 1 grain and `eth_estimateGas` a constant 21,000 — `node/api/rpc.go:160-166`. No fee market, no base fee logic (header has an optional `BaseFee` field, "Phase 2+") — `node/core/types/block.go:87`.
- Testnet chain ID 81920 and a faucet pre-fund of 1,000,000 BUCKS to a fake address built from the ASCII string "BucksDevFaucetAddress00" — `node/core/blockchain/genesis.go:84-99`. Genesis `Alloc` is never applied to any state (StateRoot left as zero hash, comment "populated after applying Alloc") — `genesis.go:115`.
- Mainnet genesis timestamp is hard-coded to 2025-01-01 and difficulty 1,000,000, gas limit 15,000,000 — `genesis.go:60-62`.

**Correctness defects in the consensus/core code (my reading of the code)**
- `BlockHeader.rlpEncode()` returns an empty byte slice (a placeholder), so `Header.Hash()` is Keccak-256 of nothing for every block. Every block, including genesis, therefore has the same hash; `parentHash` linkage and block-by-hash storage are meaningless — `node/core/types/block.go:90-103`; used in `NewBlock` at `block.go:133`, and `writeBlock` keys blocks by that hash at `node/core/blockchain/blockchain.go:174-190`.
- PoW seal hash uses a different placeholder serialization (`headerBytes`, simple concatenation, comment says "placeholder ... sufficient for the PoW scaffold") — `node/core/consensus/pow.go:253-279`. Fields like gas limit, gas used and logs bloom are not committed.
- Difficulty retarget compares `newTimestamp - parent.Timestamp` (one block interval) against the whole-window expectation of 60 s x 2016 — `pow.go:104-116`. The ratio is therefore about 2016x, so each retarget hits the +25% clamp (`pow.go:119-131`). It also never looks at the window start block. The comment "±25 % (factor of 4 ...)" and `MaxDifficultyChange = 4` (`block.go:39-40`) are inconsistent with the 3/4..5/4 clamp actually coded.
- `VerifyHeader` accepts any block at height 0 and does not check timestamps against wall clock, coinbase reward, tx root or state root; `validateBlock` only checks parent hash, height, PoW and timestamp > parent — `pow.go:67-85`, `blockchain.go:142-168`. Only "extend the head" is allowed (no forks/reorgs, no total-difficulty fork choice, although `TotalDifficulty()` exists and iterates the whole chain, `blockchain.go:232-245`).
- Block reward (`Block.Reward()`) exists but nothing pays it (no coinbase transaction/state credit) — `block.go:143-154`.
- Blocks are persisted as JSON in LevelDB (docs say a state trie and tx index also live in LevelDB; neither exists) — `blockchain.go:174-190`.

**Does it run end to end?**
- `go build ./...` compiled all packages of both modules; the `bucksnode` link step failed only because the disk was full (`strip: ... No space left on device`), so this is not a code defect. `go vet ./...` on `node/` printed nothing. `go test ./...`: node has zero test files; miner has one passing test package (`miner/engine`, 0.44 s). I ran these in a temp copy that I deleted afterwards.
- `bucksnode` startup builds genesis from hard-coded functions only: `testnet`/`devnet` use `TestnetGenesis()`, everything else `DefaultGenesis()`; there is no `--genesis` file option, and `init` merely writes a `genesis.json` that nothing reads back — `node/cmd/bucksnode/main.go:119-126,191-221`. `SaveGenesis` marshals `map[types.Address]*big.Int` (array-keyed map), which `encoding/json` cannot marshal without a TextMarshaler (I did not run it; flag as likely failure for the testnet alloc) — `genesis.go:18,161-167`.
- The built-in miner flags (`--mine`, `--coinbase`, `--threads`) populate config, but `runNode` never starts a mining loop; `Engine.Mine` is never called by the node — `main.go:94-102,128-185`. `cfg.Mining.Enabled` is unused after parsing.
- P2P (libp2p v0.33.2 + Kademlia DHT in server mode): `libp2p.New` is called with only listen addrs, NAT mapping and relay, so the identity key is ephemeral each start; `NodeKeyPath` in config and `PrivateKeyPath` in `p2p.Config` are never read — `node/core/p2p/node.go:138-146` vs `node/config/config.go:47-48`. The node registers handshake and block-sync stream handlers but never dials a handshake; the `discoverPeers` loop is an empty ticker; block sync replies with an empty list ("TODO"); `BroadcastTransaction` is a no-op; `BroadcastBlock` writes JSON to peers that never filled in `n.peers` — `node.go:166-167,242-255,316-330,339-374`. No gossipsub, no peer scoring, no handshake initiation, no validation before relaying.
- Boot nodes: none configured; genesis comments say placeholders must be replaced before mainnet; docs mention `bucks-boot.bucks.net` boot nodes — `genesis.go:65-79`, `bucks-blockchain-architecture.md` section 7. (`bucks_v1_todo.md` C-23 says the code contained placeholder peer IDs; the current code has the list empty.)

**JSON-RPC / API surface** (`node/api/rpc.go`, single HTTP POST endpoint plus `/health`; WebSocket on 8193 is documented and configured but not implemented)
- Real: `web3_clientVersion`, `net_version`, `net_listening`, `net_peerCount`, `eth_chainId`, `eth_blockNumber`, `eth_getBlockByNumber` (hex or "latest"; returns a custom reduced block shape, no tx list), `bucks_getChainParams` — `rpc.go:122-198`.
- Stubs returning constants: `eth_getBalance` always 0x0 (`rpc.go:249-252`), `eth_getTransactionCount` always 0 (`:175-177`), `eth_call` always "0x" (`:168-170`), `eth_sendRawTransaction` returns an all-zero hash without decoding (`:254-258`), `eth_getTransactionByHash/Receipt` null, `web3_sha3` returns zeros (`:215-222`), `bucks_getMithqalBalance` always "0.000..." (`:274-278`), `bucks_getSoulEngineStatus` hard-coded `connected:false` (`:193-198`), `bucks_submitWork` always returns true (`:293-296`).
- `bucks_getWork` returns [head hash, zero "seed hash", target] — the parent hash, not a header template — `rpc.go:280-291`. The miner then treats that hex as "header bytes" — `miner/rpc/client.go:136-152`. The miner/node work protocol therefore does not match; a mined nonce could not be validated by the node (no real submit path).
- Missing for any EVM tooling: `eth_getLogs`, `eth_getCode`, `eth_getStorageAt`, filters/subscriptions, `eth_feeHistory`, `eth_maxPriorityFeePerGas`, EIP-1559/EIP-155 tx handling, and `debug_`/`txpool_` namespaces. Hardhat, MetaMask and ethers need most of these.

**Config: hard-coded vs configurable**
- Configurable (TOML plus `BUCKS_` env via Viper): data dir, network name, chain ID override, P2P listen addrs, boot nodes, max peers, RPC enable/addr/ports, CORS list, mining enable/coinbase/threads, log level/format — `node/config/config.go:16-91,151-193`.
- Hard-coded: all consensus constants (reward, halving, block time, window, supply) in `types/block.go:17-47`; genesis difficulty/gas limit/timestamp/alloc in `genesis.go`; RPC returns chain ID from the constant, not from config (`rpc.go:134,148`); `/health` hard-codes "bucks-mainnet" (`rpc.go:115`); `bucks_getChainParams` hard-codes mainnet name (`rpc.go:263`). So `node.chain_id` config affects only the P2P handshake, not signatures, RPC, or genesis. There is no hard-fork/activation schedule structure (no `ChainConfig` with fork blocks).
- Miner config is TOML (`~/.bucks/miner.toml`): wallet address, node RPC URL (default `http://127.0.0.1:8192`), pool URL/worker, mode solo|pool, threads, poll interval, stale-share flag, API addr (default `127.0.0.1:8194`), logging — `miner/config/config.go:20-131,176-188`.

**Miner and GUI**
- The miner is pure Go (not C++) — `miner/` has `engine`, `stratum`, `rpc`, `api`, `stats`, `cmd/bucksminer`. Double-Keccak-256 CPU hashing with a buffer-reuse optimization — `miner/engine/hasher.go:45-95`. The stratum client implements `mining.subscribe/authorize/submit/notify/set_difficulty` (JSON-RPC-over-TCP, Stratum v1-style names despite the "Stratum v2" label) — `miner/stratum/client.go:1-13,190`. No pool server exists in the repo.
- The miner's local HTTP API exposes unauthenticated `POST /api/start`, `/api/stop`, `POST /api/config` (persists config to disk) with `Access-Control-Allow-Origin: *` — `miner/api/server.go:68-81,135-150,195-206`. Default bind is loopback, but wildcard CORS lets any web page the user visits control the miner and rewrite the payout address.
- `miner-gui/` is an Electron + Vite/React wrapper; `pkg-build/` builds a macOS .pkg installer. I did not audit these in depth.
- A separate C++ chain, "Bucks Blockchain/" at `/Users/mikado/Desktop/Bucks Core/Bucks Blockchain` (outside this clone, listed in `PROJECT_MAP.md` section 3): Bitcoin-style UTXO, SHA256d PoW, 10-minute target, 21M max (`include/consensus.h:73-82`), about 49k lines in `src/`+`include/`, with `tests/{unit,integration,fuzz,system,perf_security}`, SQLite storage, its own REST API on port 8088. `README.md` (lines 1-30) lists encrypted P2P, mempool limits, DoS scoring; `NEXT_STEPS.md:45` lists "Phase 7: Smart Contracts & Scripting" as future work. `PROJECT_MAP.md` records that the wallet, miner and Solidity contracts only work against the Go/EVM node, and that `DISTRIBUTION.md` ("C++ stable/latest") and `RELEASE_SUMMARY.md` (Go "running on devnet") disagree about which engine is production-ready.

**Wallet (`wallet/`, browser extension)**
- TypeScript/React MV3 extension; the keystore uses AES-256-GCM with PBKDF2-SHA512 at 310,000 iterations (`wallet/src/crypto/keystore.ts:4-16`, `constants.ts` KDF_ITERATIONS). The architecture doc claims Argon2id (`bucks-blockchain-architecture.md` section 8); code header says Argon2id is not natively available so PBKDF2 is used. The earlier audit's finding that seed derivation used 2,048 iterations (`bucks_v1_todo.md` C-19) appears fixed in `constants.ts` (comment says the divergence existed and was unified). The unlocked key lives in an in-memory vault, not `chrome.storage` (`wallet/src/background/vault.ts:1-5`).
- The BIP-8192 word list shipped is a deterministic placeholder stub of 2048 words; the real list is described as "proprietary ... distributed out-of-band" and absent (`wallet/src/crypto/wordlist.stub.ts:1-18`; `bip8192-wordlist-todo.md`, `bucks_v1_audit_report.md` section 1.4: the pipeline is unstarted). A wallet created with the stub cannot be recovered with the real list, and a secret word list is security through obscurity (the security of a mnemonic is its entropy, not list secrecy).
- Manifest: content script on `<all_urls>`, `all_frames`, `run_at: document_start`, and host permissions for `127.0.0.1:8192` and `*.bucks.net` — `wallet/manifest.json:26-51`.

**Contracts (`contracts/`, Hardhat + Solidity 0.8.24, evmVersion "berlin")**
- Contracts: `ContractRegistry` (owner-only name to address book), `BucksTransfer`, `BucksEscrow`, `CommunityTreasury`, `BusinessAgreement`, `SoulVerified`, interfaces `ISoulEngine`/`IContractRegistry`, library `Fees` (2,861 lines incl. tests/scripts); 4 test files (`BucksTransfer`, `CommunityTreasury`, `BusinessAgreement`, `ContractRegistry`; none for `BucksEscrow` or `SoulVerified`) — `contracts/contracts/**`, `contracts/test/*`.
- BUCKS is the native coin (contracts take `msg.value`). There is no ERC-20 / WrappedBucks, no staking or validator contract, no name registry for `.bucks`, no storage/pinning deal contract. The larger set in `bucks-contracts-plan.md` (19 contracts, e.g. WrappedBucks, GlobalProfile, MarketplaceRouter, EscrowVault, DisputeArbitration, SoulEngineOracle, publisher staking with slashing at plan lines 51-54) exists only as a plan; `bucks_v1_audit_report.md` section 1.5 confirms "No Contracts Deployed" and 21 pre-mainnet checklist items unchecked.
- Plan stores CIDs as `bytes32` (e.g. `metaCID`, `contentCID`; `bucks-contracts-plan.md` around lines 118-249). A CIDv1 does not fit in 32 bytes with its multicodec/multihash prefix, so the interface should use `bytes` (EIP-1577 contenthash style) instead.
- Deploy script deploys Registry, Transfer, Escrow, Treasury, BusinessAgreement in order and writes `deployments/<network>.json`; `deployments/` holds only `.gitkeep`, so there are no deployment addresses and no networks live — `contracts/scripts/deploy.ts:1-194`. Hardhat networks `bucks` (8192) and `bucks-testnet` (81920, defaults to the same localhost:8192 URL) — `contracts/hardhat.config.ts:30-47`. Defaults `SOUL_ENGINE_ADDRESS` to the zero address ("disabled (dev mode)") — `deploy.ts:27-28`.
- No upgradeability, pausing, or OpenZeppelin access control in the contracts (the only "upgrade" grep hit is a comment, `BucksEscrow.sol:236`); `ContractRegistry` has its own single-owner `transferOwnership` (`ContractRegistry.sol:53-56,113-117`). Escrow and agreement payouts use `.call{value:}` and set status before sending in the spots I looked at (`BucksEscrow.sol:155-168`, `BusinessAgreement.sol:375-392`), but there is no ReentrancyGuard and `BusinessAgreement` makes up to three external calls in sequence in one function; no formal audit exists.
- `protocolAdmin`/fee collector/arbiter are all the deployer EOA by default (`deploy.ts:121-123,150-153`), a single-key admin.

**Security issues (location and type only)**
- Possible secret: `contracts/.env.example:8` sets `DEPLOYER_PRIVATE_KEY=` to a 64-hex value. It is not the well-known Hardhat account #0 key (checked by comparing to that key without printing either). It may be a throwaway or a real key; treat as compromised if it was ever funded, and replace with an empty placeholder. Value not reproduced here.
- `bucks_v1_todo.md` H-19 states a Gemini API key and a `CLUSTER_SECRET` were committed earlier in git history of the wider project (not verifiable here: the clone has a single commit visible to me, `git log --all` count 1; `git log -S"AIza"` returned nothing). No other credential-pattern hits (AIza, nvapi-, PEM private keys, sk-, ghp_) in the working tree.
- `node/api/rpc.go:341-352` sets `Access-Control-Allow-Origin: *` regardless of the configured CORS list, and `Start` listens with no auth, rate limit, request body size limit or method allowlist (`rpc.go:97-111`). Default bind is 127.0.0.1 (`config.go:121-126`), but with wildcard CORS any visited web page can call the node. Once `eth_sendRawTransaction` is real this becomes a transaction-relay and DoS exposure. Also `bucks_v1_todo.md` H-20 records this.
- Miner API: same wildcard CORS and unauthenticated config write (`miner/api/server.go:135-150,195-206`).
- No transaction signature verification, replay protection or nonce handling exist server-side (`Transaction.From()` just returns a cached field, `core/types/transaction.go:60-69`); with a placeholder block hash a peer could trivially forge chain history.
- Electron/browser layer (out of scope but relevant to chain operations): `bucks_v1_todo.md` and `bucks_v1_audit_report.md` (dated 2026-08-02) list 27 critical/major issues, e.g. unauthenticated local IPFS bridge, path traversal in the updater, and `execSync` of install scripts from update tarballs. Many may have changed since.

**What is missing for a production network (derived from the above, all verified by reading the code)**
- A real header encoding and hash; a state database with a Merkle-Patricia (or equivalent) root; an EVM; transaction types, signing and mempool; block production, reward crediting, fork choice and reorgs; sync protocol; fee market; a canonical genesis file loader and chain config with fork schedule; WebSocket/filters/logs; real boot nodes with persistent peer keys; tests; chain-level monitoring (no Prometheus endpoint in the node, although the libp2p dependency tree pulls in the Prometheus client); explorer, faucet (there is only a prefunded fake address), real key custody for operators; independent security audit.

### Inferences
- With a 60 s target and halving every 210,000 blocks, the first halving would arrive after about 146 days (210,000 min) instead of Bitcoin's four years, so about 75% of supply would be issued within roughly 1.2 years at target speed. That is a design decision to revisit, not a bug.
- The honest description is "a documented design plus a skeleton", not a chain. The only maintained, tested chain engine is the C++ UTXO node, which cannot run the Solidity contracts or the Ethereum-style wallet.
- A 60 s PoW chain with a double-Keccak (ASIC/GPU-friendly, Keccak-256) hash and no existing hashrate is cheap to 51%-attack; see Q2.
- The Go node's value to the project is mainly as a place to put config and operational conventions; its consensus code should not be extended, given that a ready-made EVM stack does not need it.

### Gaps
- I did not read `miner/cmd`, `miner/engine/miner.go`/`worker.go`, `stats`, `miner-gui/`, `pkg-build/`, `QNN/`, or the Solidity bodies of `CommunityTreasury`, `BusinessAgreement`, `BucksTransfer`, `SoulVerified` in line-by-line detail; claims about them are limited to the greps and snippets cited.
- I did not run the Hardhat tests (would need `npm install`) or the wallet build, so the contract test pass rate and wallet test coverage are unknown.
- `eth_getBalance` etc. being stubs is read from code; I did not start the node.
- I did not inspect the C++ chain's tests or run it; its maturity is from its own README plus `PROJECT_MAP.md`.
- Whether the secret in `contracts/.env.example:8` is real, and whether the git history of the wider project (not this clone) still holds the Gemini key and cluster secret, needs a check against the real repo history.

## Q2. How do the main ways of launching an app-specific chain compare in 2026?

### Takeaway
For a small Go + Solidity team, the realistic options are a Cosmos SDK chain with the Cosmos EVM module (sovereign, Go, Ignite tooling, Solidity-compatible, but the PoW miner goes away), an Avalanche L1 on Subnet-EVM (sovereign EVM with a per-validator fee), or an OP Stack rollup through a RaaS provider (inherits Ethereum security, central sequencer, and browser-verifiable via Helios). Keeping a custom PoW chain means rebuilding state, EVM and sync from scratch and, at small hashrate, accepting weak security.

### Cited Findings

**Cosmos SDK + CometBFT + Ignite**
- Cosmos SDK v0.53.0 stable shipped 2025-04-29; v0.53.8 is a patch containing important security fixes and is state-breaking, so chains need a coordinated upgrade; v0.53 pairs with CometBFT v0.38.x — [Cosmos SDK v0.53 release notes](https://docs.cosmos.network/sdk/v0.53/changelog/release-notes.md), [v0.53.8 on newreleases.io](https://newreleases.io/project/github/cosmos/cosmos-sdk/release/v0.53.8) (search-result summary; the "v0.53.7 latest as of July 2026" detail came from a migration write-up I did not open).
- SDK v0.55 requires CometBFT v0.40.0; headline changes: removal of `x/params`, `x/protocolpool`, `SIGN_MODE_TEXTUAL`; reworked mempool interface; validator consensus key rotation in `x/staking`; opt-in ML-DSA-65 keys, secp256k1eth validator keys and config-driven Block-STM parallel execution; a v0.53.x to v0.55 jump can be done as one coordinated upgrade with one binary swap, handler and halt height; the page does not state whether v0.55 is stable or a release candidate — [Cosmos SDK v0.55 upgrade guide](https://docs.cosmos.network/sdk/latest/upgrade/v0.55).
- Ignite CLI GitHub release list shows v30.0.0-rc.2 (24 Sep, marked latest; year not shown on the page, presumably 2026) scaffolding chains on SDK v0.55.0, IBC-Go v11.2.0, CometBFT v0.40.0 and working with v0.55.x and v0.53.x chains; v29.10.1 (16 Jun) was the latest non-RC listed — [ignite/cli releases](https://github.com/ignite/cli/releases). So the newest Ignite is a release candidate as of this check.
- Cosmos EVM is an SDK module implementing a full EVM; docs say Hardhat, Foundry, Remix, MetaMask, ethers/web3.js work; dual hex and bech32 addresses; separate Cosmos chain ID and EVM chain ID; precompiles for staking, governance and IBC; most standard JSON-RPC methods supported but some return stub values; docs versioned v0.4.x, v0.5.0 and "next" — [Cosmos EVM docs](https://docs.cosmos.network/evm/v0.5.0/documentation/evm-compatibility/overview), [Cosmos EVM concepts](https://docs.cosmos.network/evm/next/documentation/concepts/overview).
- Ignite integrates it through an add-on app: `ignite evm add`, `ignite chain serve`; a tutorial pins Ignite 29.6.0 and the app at `evm/v0.1.2`, with 18-decimal token by default — [Ignite EVM tutorial](https://tutorials.ignite.com/integrate-the-evm-in-a-cosmos-sdk-chain-with-ignite/).

**Polkadot SDK / agile coretime**
- Bulk coretime is sold in DOT, bulk duration currently 28 days, can be split, interlaced and resold; price-capped renewal only if the region stays assigned to one parachain; on-demand cores are paid in DOT per block; the page lists no prices; last updated 2026-06-29 — [Polkadot docs: agile coretime](https://docs.polkadot.com/reference/polkadot-hub/consensus-and-security/agile-coretime/).
- A search for the current coretime price found no reliable 2026 figure; secondary articles on 2026 DOT tokenomics conflict with each other — [search result set](https://docs.polkadot.com/polkadot-protocol/architecture/system-chains/coretime).
- Crust Network, a storage-incentive layer for IPFS, is built with the Polkadot SDK — [OnFinality overview](https://onfinality.io/en/rpc-assistant/what-is-crust-network) (vendor page).

**Avalanche L1s**
- Post-Etna (ACP-77), L1 validators do not stake AVAX or validate the Primary Network; they pay a continuous dynamic L1 validator fee, initially approximately 1.3 AVAX per validator per month, rising when the total number of L1 validators passes 10,000; parameters can be changed by future ACPs and queried via `platform.getValidatorFeeConfig` — [Avalanche docs: etna changes](https://academy.avax.network/guide/etna-changes), [Avalanche blog: etna/L1 validators](https://docs.avax.network/blog/etna-enhancing-sovereignty-avalanche-l1s), [The Block summary](https://www.theblock.co/post/312121/research-unlock-unlocking-avalanche-layer-1s-with-acp-77). Sources are 2024-2025; no 2026 change found.
- The Avalanche docs page I tried for L1 setup (`docs.avax.network/avalanche-l1s`) returned HTTP 404; I could not fetch current Builder Hub launch steps.

**OP Stack / Arbitrum Orbit / RaaS**
- A July 2026 comparison describes OP Stack as the most adopted optimistic framework, at Stage 1 with permissionless fault proofs and the Superchain for interoperability; says licensing Arbitrum's stack outside Arbitrum One carries a 10% revenue share (single secondary source, confirm with Offchain Labs); says Polygon CDK is now a managed chain-as-a-service for ZK chains on AggLayer — [Protofire rollup stacks guide](https://protofire.io/guides/rollup-stacks/).
- Conduit markets itself as a self-serve RaaS for OP Stack rollups and also supports Arbitrum Orbit; Caldera supports both OP Stack and Orbit — [Conduit](https://conduit.xyz/blog/conduit-launches-arbitrum-orbit-support), [Alchemy Caldera page](https://alchemy.com/dapps/caldera). I found no published 2026 price list for either (vendor pricing is quote-based or not in the pages retrieved).
- Optimism's chain-operator docs frame running a chain as deploying L1 contracts, spinning up a sequencer and running "the full stack of services"; the landing page does not list components or tooling — [Optimism self-hosted chain operator docs](https://docs.optimism.io/operators/chain-operators/self-hosted).

**Reth / Geth private EVM**
- Reth is an MIT-licensed "modular blockchain SDK and node" (docs show v2.7.0), with a `NodeBuilder` SDK and Execution Extensions (ExEx) for indexers and off-chain services; the page lists a "Private testnets" doc and `reth dump-genesis` — [Reth docs](https://reth.rs/). The page does not describe custom chain/genesis specifics or the Engine API.

**Light clients in a browser**
- Helios (a16z) is a Rust Ethereum light client that compiles to WebAssembly and can be embedded in JS wallets/dapps; it syncs from a known beacon-chain block hash plus an untrusted RPC using sync committees (512 validators rotated every 256 epochs, about 27 h); it supports Ethereum and OP Stack networks (Optimism, Base); it does not remove the need for an RPC, and a light client does not participate in consensus. Audit status of the L1 consensus verification was stated as done, with the report to be published, unconfirmed — [a16z: building Helios](https://a16zcrypto.com/building-helios-ethereum-light-client/), [Helios site](https://helios.a16zcrypto.com/), [a16z: Helios for rollups](https://www.a16zcrypto.com/posts/article/scaling-ethereum-rollups-with-helios).

**Small PoW chain security**
- Coin Metrics treated the August 2025 Qubic episode on Monero (a claimed brief majority of hashrate, a six-block reorganization) as a stress test and argued smaller PoW networks with thin security budgets and concentrated mining are more exposed; proposed fixes included merge mining and Dash's ChainLocks — [Coin Metrics: Monero's stress test](https://coinmetrics.substack.com/p/state-of-the-network-issue-326), [Cointelegraph](https://regional-front.cointelegraph.com/news/51-attack-monero-prompts-proposal-overhaul-consensus). A claim that Ethereum Classic can be attacked for under $15,000 per hour comes from a promotional KuCoin blog and is unverified — [KuCoin blog](https://www.kucoin.com/uk/blog/id-understanding-the-moat-what-is-pow-51-attack-cost-in-2026).

### Inferences
- Effort to keep custom PoW: the Go node lacks about everything a chain needs (Q1); finishing it would mean re-implementing what Geth/Reth/Cosmos already provide. Merge mining or an existing PoW base (a Bitcoin-style fork, e.g. the C++ chain) is the only way a PoW design gets real security, and then the EVM is not available.
- Security model and validator count (background, unverified this session): CometBFT chains typically run tens to about 150 validators with one-block finality and tolerate <1/3 faulty power; Avalanche L1s can run with a handful of validators set by the L1 owner (ACP-77 makes 1 validator technically possible but weak); an OP Stack rollup inherits Ethereum for safety but its sequencer is centralized by default (single operator); a private Reth/Geth chain uses PoA (Clique/IBFT-style) with a trusted validator set.
- Browser header verification (background, unverified): CometBFT headers can be verified with the Tendermint light-client algorithm (trusted height/hash plus validator-set hand-offs, weak subjectivity) and there are JS/WASM implementations; Helios gives the same for Ethereum and OP Stack through the browser (cited above). A custom PoW chain would need a purpose-built SPV client written from scratch. Avalanche has BLS-signed warp messages that can be verified, but I found no browser light client evidence.
- EVM compatibility with existing Solidity: Cosmos EVM, Avalanche Subnet-EVM, OP Stack and Reth all run unmodified Solidity; the contracts are pinned to `evmVersion berlin` (`hardhat.config.ts:23`), which is safe on every target but should be raised to the target chain's supported fork (needs checking, because opcode support such as PUSH0 and Cancun features differs per chain). Native-coin accounting (`msg.value`) works on all; a custom gas token is needed on OP Stack (background, unverified: OP Stack supports a custom gas token; verify against Optimism docs).
- Cost ordering for a small team (rough, my judgement): Cosmos SDK L1 costs validator servers plus bootstrapping validators and tokenomics security; Avalanche L1 costs about 1.3 AVAX/validator/month plus servers; an OP Stack rollup costs L1 data/settlement gas plus sequencer/batcher/proposer infra or a RaaS fee (price unknown); a private PoA Reth chain is cheapest but trusted.
- The Bucks miner and the "gold-anchored mined coin" story fit a PoW chain only. Any non-PoW option removes the miner; the closest substitute is "storage provider / validator operator" earning rewards (see Q5).

## Q3. What is the recommendation for a small team with a Go node, a Go miner, a C++ chain and Solidity contracts?

### Takeaway
Do not extend the Go PoW scaffold. Pick Cosmos SDK + CometBFT + Cosmos EVM (via Ignite) as the main path for a sovereign chain that can run the existing Solidity contracts and reuse Go skills; keep an OP Stack rollup via RaaS as the fast alternative if Ethereum-grade security matters more than sovereignty or a native mined coin. Treat the C++ UTXO chain as a separate store-of-value experiment, not the base for the hosting network.

### Cited Findings
- Cosmos EVM runs standard Solidity tooling inside an SDK chain and exposes staking/governance/IBC precompiles — [Cosmos EVM docs](https://docs.cosmos.network/evm/v0.5.0/documentation/evm-compatibility/overview).
- Ignite scaffolds SDK v0.55/CometBFT v0.40 chains but its latest tag is a release candidate (v30.0.0-rc.2); the stable 29.x line was used by the EVM tutorial — [ignite/cli releases](https://github.com/ignite/cli/releases), [Ignite EVM tutorial](https://tutorials.ignite.com/integrate-the-evm-in-a-cosmos-sdk-chain-with-ignite/).
- v0.53.8 carries important security fixes and is state-breaking, so even the stable line needs coordinated upgrades — [v0.53.8 notes](https://newreleases.io/project/github/cosmos/cosmos-sdk/release/v0.53.8).
- Helios can verify Ethereum and OP Stack data in a browser; a comparable verified path for a Cosmos EVM chain was not found in this research — [a16z Helios](https://a16zcrypto.com/building-helios-ethereum-light-client/).

### Inferences
- Ranking for this team (my judgement):
  1. Cosmos SDK + Cosmos EVM, Ignite for scaffolding. Pros: Go, sovereign parameters (genesis, staking, gov, upgrades via `x/upgrade`), IBC to other chains, Solidity contracts unmodified, precompiles for staking/governance contract hooks, instant finality helpful for name resolution and storage deals. Cons: you must recruit and incentivise validators; Cosmos EVM is a younger module with stubbed RPC methods; version churn (v0.53, v0.54, v0.55 all in play); browser light-client path needs work.
  2. OP Stack rollup via Conduit/Caldera (or a similar provider): fastest to a production-grade EVM with Ethereum security and Helios verification for browsers; cons: central sequencer, ongoing L1 data costs, native BUCKS would be a custom gas token or an ERC-20, and no mining.
  3. Avalanche L1 (Subnet-EVM): sovereign EVM with a small validator set and a per-validator AVAX fee; cons: tied to AVAX economics, less natural for a Go-Cosmos style on-chain governance, and no browser light client evidence.
  4. Private Reth/Geth PoA: only for devnet/testnet.
  5. Keep PoW: only if a mined, gold-anchored coin is a hard product requirement; then use the C++ chain (it exists, is tested and Bitcoin-compatible in design) as a separate money layer and bridge to the EVM chain later.
- Migration path for existing assets: contracts (Solidity 0.8.24, 4 test suites) port as-is; wallet needs only the new chain ID/RPC and EIP-1559 handling; the Go node and miner become the "bucksd operator" tooling and a storage-provider client; BIP-8192 stays a wallet concern.
- Sequence: devnet on Ignite, testnet with 4 to 7 foundation validators, port contracts, add name registry and storage-deal contracts, run an external audit, then mainnet. Budget the audit and validator onboarding before the chain.

### Gaps
- No evidence on cost per month for any option, no benchmarks, and no team-size/time estimates from sources; the ranking is judgement.
- Whether "BUCKS = mithqal-of-gold-weight, mined, 21M" is a hard requirement is a product decision I cannot see; it flips the ranking.

## Q4. What should a chain configuration and operations platform (operator console) do?

### Takeaway
Build the console as a thin control plane around standard tooling: a typed network-profile and genesis builder with validation and diffing, reproducible provisioning (containers or systemd units generated from the profile), Prometheus/Grafana plus an explorer, a custody layer that separates deployer, validator and treasury keys, and a staged upgrade flow. Most of this is design, not sourced fact; the sourced anchors are the chain-config surface of each stack.

### Cited Findings
- Cosmos side: validator consensus key rotation exists in SDK v0.55 `x/staking`; upgrades are driven by an upgrade handler and halt height, and the guide recommends testing on a mainnet-state export before scheduling — [Cosmos SDK v0.55 upgrade guide](https://docs.cosmos.network/sdk/latest/upgrade/v0.55).
- Cosmos EVM has two chain IDs (Cosmos string ID and integer EVM ID), dual-address accounts and precompiles; genesis and module params must set both — [Cosmos EVM concepts](https://docs.cosmos.network/evm/next/documentation/concepts/overview).
- Avalanche exposes the L1 validator fee config on-chain at `platform.getValidatorFeeConfig`, so a console can read fee parameters programmatically — [etna changes](https://academy.avax.network/guide/etna-changes).
- Reth documents `reth dump-genesis` and private testnet guides and an ExEx framework for building indexers/explorers off-chain — [Reth docs](https://reth.rs/).
- Filecoin's PDP Explorer lets anyone check proof status, fault history and provider performance — [Filecoin Onchain Cloud is live](https://filecoin.io/blog/filecoin-onchain-cloud-is-live-on-mainnet), a pattern to copy for a Bucks storage dashboard.
- Local starting points to reuse: node TOML config + env overrides (`node/config/config.go:151-193`), miner TOML and local API (`miner/config/config.go`, `miner/api/server.go`), Hardhat deploy script that writes `deployments/<network>.json` (`contracts/scripts/deploy.ts:176-188`), and the browser's keystore/wallet code (OS keychain via keytar in `bucks-browser-architecture.md:151,580`).

### Inferences (design)

**1. Network profiles.** A profile is a signed, versioned JSON/TOML document: `{name, kind: devnet|testnet|mainnet, chain_ids {cosmos, evm}, genesis_ref (hash), seeds, rpc_endpoints, explorer_url, denom/decimals, contract_addresses, min_client_version, checkpoint {height, hash, valset_hash}}`. Ship as a file in the repo plus an IPFS CID, signed by a multisig, so the browser can fetch and verify it. Devnet is one-click local (docker compose or `ignite chain serve`), testnet is the public staging with a faucet, mainnet is locked behind two-person approval.

**2. Genesis builder and parameter editor.** Form + raw view backed by a JSON schema per stack (Cosmos genesis modules: auth, bank, staking, gov, mint/emission, slashing, evm, feemarket, distribution, plus custom `x/names`, `x/storage` if added). Validations: supply sum equals the sum of all allocations; no allocation to the zero or the fake address; vesting schedules sane; chain IDs unique against a public registry (e.g. chainlist) and not 8192/81920 conflicts with existing registrations (check before launch); block time vs timeout params consistent; gas limit and min gas price set; unbonding time > checkpoint expiry; validator set size and voting-power concentration warnings (no one over 1/3, no top-3 over 2/3); gentx collection with signature checks; deterministic genesis hash printed and pinned. A diff view between profile versions and a "dry-run" that boots a throwaway local net from the genesis and runs smoke tests (create tx, deploy registry contract, resolve a name).

**3. Node, miner and validator provisioning and health.** Inventory of hosts with roles (validator, sentry, RPC, seed, archive, indexer, storage-provider). Generate configs and unit files from the profile (never hand-edit on hosts); signed release manifest with binary hashes (reuse the browser's CID-based updater idea but fix the audited issues first). Health checks: height lag, peers, missed blocks, signing status, mempool size, disk, version, upgrade-plan awareness. For storage providers: pinned bytes, proof success rate, retrieval latency. Existing Go miner becomes a "provider agent" if PoW is dropped.

**4. Key custody.** Separate roles: deployer/admin multisig (Safe-style contract or a Cosmos multisig with threshold 3-of-5, hardware wallets), validator consensus key on remote signer with HSM/KMS (e.g. tmkms/horcrux-style or cloud KMS; background, unverified), operator/withdraw keys cold, faucet hot key with a small balance and rate limits, release-signing key offline. Browser wallet keeps OS-keychain storage; console never holds user keys. No private keys in `.env` files (the repo's `.env.example` pattern is the anti-pattern flagged in Q1); use a secrets manager and short-lived deploy keys. All admin actions (param changes, contract upgrades) go through on-chain governance or a timelocked multisig with a public delay.

**5. Faucet.** Testnet only; rate limit per address/IP/OIDC identity, a daily cap, captcha-free allowlist for developers, balance alarms. Mainnet has none.

**6. Block explorer.** Do not write one from scratch: use Blockscout (open-source EVM explorer, background, unverified here) or Ping.pub/Mintscan-style for the Cosmos side, plus a custom tab for names and storage deals fed by events. Index with an ExEx-style or event-subscribing indexer into Postgres; expose a GraphQL/REST API for the browser.

**7. RPC endpoint management.** A pool behind a load balancer with health-based routing, per-key rate limits, method allowlists (no admin/debug on public RPC), WebSocket support, pruned and archive tiers, and a published endpoint list inside the signed profile. Fix the current "single unauthenticated endpoint with wildcard CORS" pattern: origin allowlist for `bucks://` and the app origin only, auth for admin methods, body size limits.

**8. Contract deployment and verification.** Pipeline: compile with pinned compiler (0.8.24) and evmVersion for the target chain, run tests and static analysis (Slither-class), deploy through CREATE2/deterministic factory for stable addresses across devnet/testnet/mainnet, write `deployments/<profile>.json` and pin it to IPFS, publish source + metadata to the explorer's verification API (and Sourcify, background, unverified), register in `ContractRegistry` (or ENS-like registry), transfer ownership to the governance multisig, and record bytecode hashes in the signed profile. Add proxies (UUPS/transparent) or immutable-with-migration deliberately; the current contracts are non-upgradeable (Q1).

**9. Upgrade and migration flow.** Three tracks: (a) binary upgrades via on-chain upgrade proposal + halt height (Cosmos pattern from the v0.55 guide: one handler, rehearsed on a state export); (b) contract upgrades via proxy + timelock, or deploy-new + migrate-data with a pause; (c) the migration off the current scaffold: there is no mainnet state, so a clean-slate genesis is possible, but if testnet balances matter, export/import via a snapshot-to-genesis tool. Release checklist: testnet soak of N days, validator signaling threshold, rollback plan, public changelog.

**10. Observability.** Chain metrics via CometBFT/SDK Prometheus endpoints (background, unverified) or node exporters; Grafana dashboards: height, block time, missed blocks, validator participation, mempool, peer count, RPC latency/error rates, disk growth, contract events (names registered, deals opened, proofs failed), faucet balance. Alerting to on-call; log shipping; uptime probes from several regions; a public status page. The Go node currently exposes no metrics.

**11. Backup and restore.** Validator key backups in sealed form (never in the same place as the state), periodic state snapshots (IPFS-pinned and hashed) so a new node syncs in minutes, config/profile in git, a tested restore drill each quarter, and a documented "validator key moved" procedure that avoids double signing.

**12. Security controls.** RBAC with SSO; every console action produces a signed, append-only audit log; four-eyes approval for mainnet changes; secret scanning in CI; dependency pinning; SBOM and signed binaries; rate limiting and WAF on public RPC; separate network zones; bug bounty; external audit of contracts and of the console's deploy paths before mainnet. Fix the cited local issues first (wildcard CORS on node and miner APIs, unauthenticated config writes, private-key placeholder in `.env.example`).

**13. Minimal build plan for the console.** Start as a CLI + web UI over a Go library (`bucksctl`) that reads/writes profile files and wraps `ignite`/`bucksd`; avoid building a SaaS. Phase 1: profile + genesis builder + devnet; Phase 2: provisioning + monitoring + faucet + explorer; Phase 3: custody integrations and upgrade orchestration; Phase 4: governance UI.

### Gaps
- No primary-source documentation fetched this session for Prometheus metric names, tmkms/Horcrux, Blockscout, Sourcify, Safe or Cosmos multisig; those mentions are background.
- No benchmark of how heavy an operator console of this scope is; effort estimates are not provided.
- I did not review hosted "chain-as-a-service" consoles (Conduit, Caldera, Ignite Apps) in detail; their feature sets may cover some of this out of the box.

## Q5. How should on-chain naming, storage incentives and verified browser resolution work for IPFS hosting?

### Takeaway
Use a name registry that stores EIP-1577-style contenthash/IPNS records and follows ENS conventions, reachable from the browser through either a light-client-verified read or an RPC read checked against signed checkpoints; add a storage-deal registry that pays providers on successful proofs (Filecoin PDP is the closest working reference); verify results in the browser with a signed checkpoint plus a header/state proof rather than trusting one RPC.

### Cited Findings

**Name registries**
- ENS: ENSv2 contracts were "100% written with 98% test coverage" and with auditors in ENS Labs' Q1 2026 report; ENS Labs dropped the Namechain L2 in February 2026 and is deploying ENSv2 directly on Ethereum mainnet; a mainnet launch date was not found — [The Block](https://www.theblock.co/post/388932/ens-labs-scraps-namechain-l2-shifts-ensv2-fully-ethereum-mainnet), [ENS Labs quarterly reports](https://discuss.ens.domains/t/ens-labs-quarterly-progress-reports/20565/7), [Radom summary](https://www.radom.com/insights/ens-labs-revises-strategy-by-halting-development-of-namechain-layer-2-opts-for-full-integration-of-ensv2-on-ethereum-mainnet).
- EIP-1577 contenthash: value is `<protoCode uvarint><value>`; IPFS uses code `0xe3` and Swarm `0xe4` with a CIDv1 without base prefix; resolvers advertise interface id `0xbc1c58d1`; the page does not define an IPNS prefix in its text, and the EIP's status is "Stagnant" — [EIP-1577](https://eips.ethereum.org/EIPS/eip-1577).
- EIP-3668 CCIP-Read (Final): a contract reverts `OffchainLookup(sender, urls, callData, callbackFunction, extraData)`; a client calls the gateway URL (GET with `{data}` or POST) and then the callback, where the contract must verify the response (Merkle proof or trusted signature); clients should cap lookups (at least 4 recommended) and disable CCIP-Read for transactions by default; gateway requests leak user IP to the operator — [EIP-3668](https://eips.ethereum.org/EIPS/eip-3668).
- EIP-4804 `web3://` URL scheme (listed as Final): `web3://[user@]contract[:chainid]/method/args?returns=...`, names ending in a provider suffix (e.g. `.eth`) are resolved through the name service, with resolve modes `auto` and `manual`; read-only calls only — [EIP-4804](https://eips.ethereum.org/EIPS/eip-4804).
- Unstoppable Domains: became an ICANN-accredited registrar (Aug 2024) and has de-emphasised blockchain names, which are no longer the default in its storefront, while pursuing DNS TLDs; it reports over four million blockchain names sold — [DomainIncite](https://domainincite.com/?p=31583), [ForkLog](https://forklog.com/en/unstoppable-domains-halts-plans-to-integrate-crypto-and-bitcoin-into-dns/).
- Solana Name Service: `.sol` names, one-time payment with no renewal (undated aggregator description) — [Solana Compass](https://solanacompass.com/projects/solana-name-service-sns).
- Handshake: root-zone (TLD-level) naming, niche adoption; mainnet launched February 2020 — [CoinDesk](https://coindesk-coindesk-prod.cdn.arcpublishing.com/markets/2020/02/04/handshakes-uncensorable-web-domains-go-live-on-mainnet/), [CryptoSlate](https://cryptoslate.com/handshake-mainnet-goes-live/); no 2026 adoption figures found.

**Storage incentives**
- Filecoin Onchain Cloud: Filecoin's own blog dated 2026-03-26 says it is live on mainnet; Proof of Data Possession (PDP) uses drand-derived randomized challenges verified on-chain by a contract; Filecoin Warm Storage Service uses PDP, and Filecoin Pay adjusts payments from PDP results (FIL, USDFC or any ERC-20, streaming epoch payments that pause on failed proofs, per a secondary overview); PDP Explorer is public; Storacha Forge uses it — [Filecoin Onchain Cloud is live on mainnet](https://filecoin.io/blog/filecoin-onchain-cloud-is-live-on-mainnet), [Filecoin PDP docs](https://docs.filecoin.io/provide-storage/pdp/about), [BlockEden overview](https://blockeden.xyz/blog/2025/11/25/filecoin-onchain-cloud-enters-the-decentralized-infrastructure-race/). Launch dates differ by source (November 2025 testnet, January 2026, March 2026 mainnet).
- Crust Network: Polkadot-SDK chain acting as an incentive layer for IPFS pinning; MPoW (Meaningful Proof of Work, TEE-based) verifies storage, GPoS ties staking quota to storage; storage is bought in an on-chain order market; replica counts and prices are operator-set (vendor-sourced "30+ replicas") — [OnFinality](https://onfinality.io/en/rpc-assistant/what-is-crust-network), [IPFS forum thread](https://discuss.ipfs.tech/t/crust-network-decentralized-pinning-service-of-ipfs/12689). No 2026 Crust news found.
- Arweave: one-time upfront payment into an endowment, guarantee framed as at least 200 years or as long as the endowment holds; sources disagree on the split (about 15% paid out vs 85% endowment is one claim) and the assumed cost decline (30.57% to 38% per year vs the protocol docs' 0.5% break-even assumption) — [Arweave permaweb journal: storage endowment](https://permaweb-journal.ar.io/reference/storage-endowment.html), [ArDrive](https://ardrive.io/articles/can-data-really-be-stored-forever/).
- Codex: erasure coding, lazy repair, ZK-based remote auditing and incentive mechanisms; marketplace defined by a smart contract on an EVM chain, validators enforce proof submission and penalties; the marketplace spec is a "raw" draft; the repo describes itself as pre-alpha; a 2025 mainnet target could not be confirmed as met — [Vac RFC: Codex marketplace](https://rfc.vac.dev/codex/raw/codex-marketplace), [free.technology](https://free.technology/codex).

**Browser verification primitives**
- Helios (above) shows a trust-minimized, WASM-capable light client verifying a chain from a checkpoint (a known beacon block hash) plus untrusted RPC — [a16z: Helios](https://a16zcrypto.com/building-helios-ethereum-light-client/).

### Inferences (design)

**Name registry (`BucksNames`).** ENS-like but smaller: ERC-721 name NFTs, a registry mapping `namehash -> (owner, resolver, expiry)`, a resolver storing `contenthash` (EIP-1577 bytes: IPFS `0xe3` CIDv1; IPNS `0xe5` in the multicodec table, background, unverified in this session), `text`, and `bucks:signing-key`. Support `.bucks` TLD only in the first release, with a commit-reveal register function, annual rent in BUCKS or a lifetime price (SNS-style) decided in tokenomics, grace and release periods, reserved list, and registrar controlled by governance. Subnames (`app.name.bucks`) as in ENS. Reverse records (address to name). Do not store CIDs as `bytes32` (Q1).

Comparison summary:
- ENS: best standards and tooling, Ethereum-secured, costly names; adopt its interfaces so wallets and libraries work (EIP-1577, EIP-3668, ENSIP-style text records).
- Handshake: owns the actual DNS root with TLD auctions; browser support needs HNS resolvers and its own PoW chain; heavy for this project.
- Unstoppable: trending toward ICANN DNS; vendor-controlled; skip.
- Namecoin: no 2026 evidence retrieved; background only, a Bitcoin-fork name database with expiring names; skip or gap.
- SNS: cheap, one-time fee, Solana-specific; model is attractive for pricing only.
- Lens: social-graph handles; no evidence retrieved; not a naming solution for hosting.

**Resolution in the browser for `bucks://` and `.bucks`.** Flow: (1) parse the name; (2) call the registry on the Bucks chain (or an L1 ENS root pointing to the Bucks resolver using CCIP-Read, which also gives compatibility with `.eth` clients); (3) verify the answer: either a light client on the browser (CometBFT light client or Helios if using OP Stack) that checks the header and a storage proof of the name record, or, simpler, a signed checkpoint: the foundation multisig and validators sign `(height, block_hash, registry_state_root)` every N blocks; the profile pins the latest checkpoint and the browser verifies the Merkle-Patricia proof from `eth_getProof` against it; (4) obtain the CID or IPNS key; for IPNS, verify the IPNS record signature and sequence; (5) fetch content through the local IPFS node and verify CID hashes as the content streams in; (6) display a lock state: "verified by light client/checkpoint at height H" vs "unverified RPC". Never trust a single RPC; use 2+ endpoints and compare. Also implement `web3://` (EIP-4804) as an alternative address form for contract-served pages.

**Storage-deal / pinning-incentive registry (`BucksStorage`).** Contracts: `ProviderRegistry` (stake, capacity, endpoint, region), `DealMarket` (client posts CID, size, duration, replication, price and escrow; providers accept), `ProofVerifier` (challenge by on-chain randomness: drand or block hash, provider submits a proof), `Payments` (stream or per-epoch payout, slash on fault), `Reputation` (rolling success rate). Reuse designs: Filecoin PDP + Filecoin Pay (periodic challenge-response, payment pauses on failure), Crust (staking-bound capacity and an order market), Codex (erasure coding + ZK audit), Arweave (prepaid endowment as an option for "permanent" tier). Decision for v1: use a PDP-style Merkle challenge scheme (sample random 32-byte leaves of the CAR/blocks and verify a Merkle path on-chain) and slash stake for repeated misses; avoid TEE (Crust) and ZK (Codex) until needed. Alternative: integrate Filecoin Onchain Cloud directly for cold storage and use Bucks contracts only for naming, pins and payments, if the cost of running a proof system is too high (judgement).

**Proof-of-retrievability options.** (a) PDP/Merkle challenge (cheap, proves possession, not retrievability); (b) retrieval probes by watchers (off-chain measurements aggregated on-chain by a quorum; proves delivery speed but is gameable); (c) PoRep/PoSt as in Filecoin (heavy); (d) ZK audits (Codex; immature); (e) TEE attestations (Crust; hardware trust). For a small team: (a) + (b) with a bonded watcher set.

**On-chain governance of parameters.** Name price, deal limits, slashing rates, challenge frequency, and checkpoint signer set changed only through the timelock described in Q4.

### Gaps
- No primary-source evidence retrieved for Namecoin, Lens, or the current multicodec code for IPNS (so `0xe5` is background and must be checked against the multicodec table); no 2026 data for Handshake adoption or Crust activity; Codex mainnet status unconfirmed.
- No verified browser implementation of a CometBFT light client in JS/WASM; Helios covers Ethereum/OP Stack only (cited). If Cosmos EVM is chosen, the checkpoint-plus-proof approach above is the safer assumption until a light client is validated.
- I could not confirm whether EIP-4804 is Final or Last Call at this moment beyond what the fetched page showed.
- Prices/revenue-share numbers (Orbit 10%) are single-source and unverified.
