# Bucks can host the web, if it fixes five things first

Bucks Browser can credibly become a browser that fetches, verifies and serves sites by CID (content identifier) instead of by server address, but today it is a good *reader* of IPFS and not yet a *host*, and five findings decide what to do first. (1) **The upstream is shaky**: Interplanetary Shipyard, the team that maintained Kubo, Helia, Boxo and the public gateways, ended its IPFS work on 30 Sep 2026 and named no successor, so Bucks must pin versions and run its own routing and fallback infrastructure ([Shipyard](https://ipshipyard.com/blog/2026-the-end-of-ipfs-at-shipyard/)). (2) **There is no working Bucks chain**: the Go node in `buckscore` is a scaffold (placeholder block hash, stubbed balances, no EVM, no state, no mining loop), so a base-chain decision must precede any chain platform. (3) **Hands-on measurement**: Kubo's `_redirects` file makes history-router single-page apps work on the subdomain gateway, but the same site returns 404 for every deep link through Bucks' current path-gateway proxy; hash-router apps and static sites pass everywhere. (4) **Security gaps in code**: silent fallback to a public gateway, unauthenticated IPC, unencrypted wallet keys, agent publish tools that run without approval, an `exec()` of code fetched by CID, and secrets leaked from the older line. (5) **A browser agent needs architectural defences**, not keyword filters: vendors concede prompt injection will not be fully solved. The recommended path is a 5-phase roadmap (about 35 to 45 person-weeks to a hosting-capable, agent-safe browser, before the chain), starting with a one-to-two-week safety and measurement phase and the owner decisions listed at the end. All effort figures are my estimates, not measurements.

## How to read this report

Evidence comes from six research notes in the notes folder (network availability, web hosting, hands-on experiment, agentic security, codebase gap audit, blockchain platform). Claims with web sources carry links. Claims about code or measurements trace to a named note: "experiment" means a command run on this machine on 19 Oct 2026; "audit" means code read at the file and line given in the audit note; both are marked as read or measured, not run in Electron. I label my own reasoning "inference". I print no secret values; only the type and location of leaked secrets is named.

A short glossary, since hosting terms matter for the decisions below. A **CID** is a content identifier: a fingerprint of the bytes, so `ipfs://<cid>` always means exactly those bytes and any client can check them. **Pinning** means telling a node to keep a CID and never garbage-collect it; content that nobody pins eventually disappears. A **gateway** is an HTTP server that turns a CID request into a web response; the browser itself acts as a gateway when it handles `ipfs://`. **IPNS** is a mutable pointer: a key pair signs "this name now points to CID X", so one address can follow your updates; records expire after about 48 hours in the DHT unless the publisher keeps re-publishing ([IPNS spec](https://specs.ipfs.tech/ipns/ipns-record/)). **DNSLink** does the same job through a DNS TXT record, so `example.com` can point to a CID. The **DHT** (distributed hash table) is the public phone book mapping CIDs to the nodes that hold them; provider entries live 48 hours and must be re-announced about every 22 hours ([Kad-DHT spec](https://specs.ipfs.tech/routing/kad-dht/)).

## The IPFS foundation is moving under Bucks' feet

The most decision-relevant external fact is organisational. Shipyard announced on 24 Aug 2026 that its last day of IPFS work would be 30 Sep 2026 after Protocol Labs did not renew funding; the work ended covers Kubo, Helia, Boxo, Rainbow, IPFS Desktop and Companion, Someguy, the Service Worker Gateway, plus operations of ipfs.io, dweb.link, delegated-ipfs.dev and bootstrap nodes ([Shipyard](https://ipshipyard.com/blog/2026-the-end-of-ipfs-at-shipyard/)). The Kubo v0.43 changelog calls v0.43 the last release with new features from the Shipyard team and says no one at Shipyard maintains Kubo afterwards ([Kubo v0.43 changelog](https://raw.githubusercontent.com/ipfs/kubo/master/docs/changelogs/v0.43.md)). The IPFS blog says ipfs.io and dweb.link are not fully shut down but redirect browsers to a service-worker gateway and are rate-limiting hotlinked and backend traffic, "increasing" ([IPFS blog](https://blog.ipfs.tech/2026-08-beyond-sponsored-gateways/)). The Service Worker Gateway is now kept alive by two individuals for the IPFS Foundation ([repo](https://github.com/ipfs/service-worker-gateway)), and forum users reported on 4 to 6 Oct that dist.ipfs.tech, ipfscluster.io and trustless-gateway.link were down ([forum thread](https://discuss.ipfs.tech/t/what-happens-to-ipfs-maintenance-and-public-infrastructure-after-september-30/20324)). The experiment saw the same weakness first-hand: dist.ipfs.tech timed out for Bucks' own Kubo download script, which succeeded only through its GitHub fallback.

Source quality varies and the report should not overstate it. The Shipyard post and Kubo changelog are primary. Cryptobriefing and Cointelegraph (secondary) add that Protocol Labs moves to smaller individual maintainer grants ([Cryptobriefing](https://cryptobriefing.com/shipyard-ipfs-protocol-labs-funding-ends/)); that part is single-source. Claims that Infura closed its IPFS service on 15 Aug 2026 and that Cloudflare closed its gateway in 2024 appear only in one blog ([byteiota](https://byteiota.com/ipfs-shipyard-shuts-down-what-developers-must-do-now/)), are uncorroborated, and the Cloudflare one conflicts with Cloudflare's own documentation; treat both as unverified. A single forum user claimed (10 Oct) that new releases came from new maintainers; unverified. The notes disagree on one point: one source says Protocol Labs "takes back" ipfs.io operations, while the IPFS blog says the gateways are redirected and rate-limited, so the safe reading is "degrading, future unknown". Fleek's hosting also closed on 31 Jan 2026, and the IPFS project itself now uses GitHub Pages, Kubo CAR creation, IPFS Cluster pinning and DNSLink ([IPFS docs](https://docs.ipfs.tech/case-studies/fleek/)). Brave removed its bundled node in Aug 2024 citing under 0.1% usage ([Brave](https://brave.com/ipfs-support/)), a reminder that the audience for native IPFS is small and that Bucks has no browser-vendor ally.

The protocol itself is healthy. ProbeLab's 2026 digests show DHT lookups averaging just over 0.3 s, publish times under one second on Kubo 0.39 and later, and 23k to 25k DHT servers ([ProbeLab Wk 29](https://discuss.ipfs.tech/t/probelab-s-notable-ipfs-performance-results-week-29-2026/20276)). The risk is maintenance and public infrastructure, not the network. The implication (inference) is a "thin embedding" strategy: pin Kubo to a vetted version with embedded hashes (today Bucks downloads the latest release and checks a SHA-512 served from the same host, per the audit), talk to Kubo only through its HTTP RPC and config, run Bucks' own bootstrap and delegated-routing endpoints, and budget security-patch work, given that 2026 Kubo advisories exist (one CVE reported through a weak, snippet-only source).

## Hosting feasibility: what was measured, what fails

The experiment ran Kubo 0.43.1 in an isolated repo on loopback, with headless Chromium and the real Bucks protocol handler imported under a stub; it could not run inside Electron, because installing Electron 44 failed with "No space left on device" (the volume had about 117 MiB free). The Go build of the chain notes also failed at link time for the same reason. **The owner should free disk space before any further builds or end-to-end runs.** All timings are loopback numbers and show correctness, not network performance.

The central result concerns single-page apps. A history-router SPA returns 404 on cold deep links on every gateway by default. Adding a `_redirects` file with `/* /index.html 200` fixes it on the **subdomain** gateway (`<cid>.ipfs.localhost`), where Chromium rendered every route, and also enables 301/302 rules and a custom 404; it does nothing on the **path** gateway. Bucks proxies the path gateway, so through the real handler `/about`, `/users/42`, the 301 rule and the custom-404 rule all returned 404 (experiment note, sections 2 and 6). Limits on `_redirects` in Kubo 0.43.1: forced rules (`!`) produce HTTP 500 for every request that reaches rule evaluation, a malformed line produces 500 on non-existing paths, and files over 64 KiB are rejected; a catch-all rule also mislabels unknown `.png` paths as `image/png` with an HTML body. The IPFS spec says `_redirects` applies on subdomain and DNSLink gateways "and on browsers with native ipfs:// and ipns:// handlers", so Bucks, as a native handler, is expected to implement it ([spec](https://specs.ipfs.tech/http-gateways/web-redirects-file/)). The experiment found two ways: proxy to `http://<cid-base32>.ipfs.localhost:<port>` (verified from Node fetch; needs base32 CIDv1 and base36 IPNS keys, and DNSLink label encoding which was untested), or parse `_redirects` in the handler.

Origin isolation was the second finding. On the subdomain gateway each CID is a separate secure-context origin with separate localStorage, IndexedDB, cookies and service-worker scope; on the path gateway every CID shares one origin and site B read site A's storage and cookies. An IPNS subdomain kept its origin and localStorage after the name was repointed to new content. Bucks gets per-CID origins from its `standard`, `secure` scheme registration (audit, `protocols/index.js`), which matches the Electron docs ([Electron protocol](https://www.electronjs.org/docs/latest/api/protocol)), but that is a code-level conclusion; the origin probes still have to be run inside Electron 44. Service workers are disabled for both schemes (`allowServiceWorkers: false`), so PWAs that register one will fail under `ipfs://`, a product decision (D4 below). Neither Kubo nor Bucks adds a Content-Security-Policy; Kubo sends `nosniff` only on raw responses and Bucks drops that header.

Other measurements reassure. A 2,500-file, 60 MB site added in 0.64 s; a 50 MB file served with ~1 ms time-to-first-byte and correct range requests (206/416), so video seeking works; Kubo shards directories automatically past roughly 256 KiB of directory entries (HAMT, around 3,000 to 4,000 entries here). Updates are cheap: a CSS edit created 2 new blocks of 14, and a 1-byte edit inside a 50 MB file created 3 new blocks. IPNS publish and resolve took about 20 to 25 ms offline, and the same-origin storage persisted across republish. Two sharp edges: files edited through MFS (Kubo's mutable file system) hash differently from a clean `ipfs add` of identical content (dag-pb versus raw leaves), which matters for reproducible deploys; and if one block of a large file is missing, the gateway sends `200` headers and then silently truncates the body (and returns 500 for ranges inside the gap), a failure Bucks does not detect. Online with no provider, Kubo waits a blind 30 s before returning 504 unless `Gateway.NoFetch` is set.

The honest scope statement for the owner: Bucks can make every static and client-side app hostable by CID, and the Uniswap interface is the standing proof that a wallet-authenticated client-side app can be shipped per release by CID with IPNS, DNSLink and ENS pointers ([Uniswap](https://blog.uniswap.org/uniswap-interface-ipfs)). Anything with server state remains a hybrid. Availability, not capability, is the dominant risk: unpinned content is garbage-collected, and the experiment showed `ipfs repo gc` turning a site into a 404 within milliseconds.

## Making every Bucks node a host: configuration, durability and naming

The final repository's Kubo configuration is shaped for device pairing, not hosting. It sets loopback API and gateway ports, a random reserved swarm port, pubsub with gossipsub, mDNS and peering, and initialises the repo with the `lowpower` profile; it sets nothing for routing, providing, AutoNAT, relay, hole punching, port mapping, storage maximum or gateway behaviour (audit §1, verified by grep). What `lowpower` changes was not verified in the notes, so whether the node announces content to the swarm at all is an open test, not a conclusion. A published site would also vanish whenever the author's laptop sleeps.

The recommended desktop profile below is my synthesis from Kubo's documented defaults ([Kubo config](https://raw.githubusercontent.com/ipfs/kubo/master/docs/config.md)) and is not a published recommendation. Keep `Routing.Type=auto` (client or server by reachability), leave `AcceleratedDHTClient` off (it crawls the full DHT hourly, a poor fit for laptops), keep the sweeping provider, set `Provide.Strategy` to `pinned+mfs` so visited-but-unpinned blocks are not announced, set `Datastore.StorageMax` to a user quota, restore Kubo's default swarm behaviour for port mapping, and set `Gateway.NoFetch=true` on any gateway reachable by pages so it is not an open fetch-proxy. Reachability will be partial: a 4.4 million-attempt measurement found about 70% hole-punch success conditional on getting a relay reservation, with symmetric NAT near 40% and about 36% of NAT'd peers never obtaining a reservation ([arXiv 2510.27500](https://arxiv.org/pdf/2510.27500); [ProbeLab](https://probelab.io/blog/can-libp2p-punch-through-nats/)). Circuit relays default to 2 minutes and 128 KB, enough for signalling, not bulk transfer. Churn is high: about 60% of DHT servers stay online 1.5 hours or less ([ProbeLab talk](https://probelab.io/talks/measuring-the-web30-stack/)).

That evidence supports a three-tier durability design (inference, no 2026 precedent found for laptop-fleet pinning pools). **Tier 1, the user's own devices**: Bucks already pairs devices; add reciprocal pinning, with a size cap, because today `devices.autoPin` is unbounded. **Tier 2, an always-on anchor**: at least one Bucks-operated Kubo or IPFS Cluster peer plus one commercial pinning service through the vendor-neutral Pinning Service API, which Kubo supports natively ([spec](https://github.com/ipfs/pinning-services-api-specs)); Pinata is named by the IPFS blog as a recommended provider ([IPFS blog](https://blog.ipfs.tech/2026-08-beyond-sponsored-gateways/)) and avoids repeating the Fleek lock-in. Vendor prices in the notes are unconfirmed. **Tier 3, a community pool**: laptops as quota-limited follower peers or opt-in cache pins. A simple model (assumption, not measurement) shows why tier 2 is mandatory: if each laptop is online 30 to 50% of the time, three independent replicas give roughly 66 to 88% availability, and independence fails for users in one time zone. Laptops add bandwidth offload and locality; they do not add durability.

Naming has three layers. IPNS keys give a stable address per site and, as measured, a stable web origin; the publisher must stay online or delegate republishing, because records expire in 48 hours. DNSLink gives human names via DNS. A chain registry gives names that need neither DNS nor a key held in the browser; no name-to-CID contract exists today (`ContractRegistry` maps names to contract addresses), and `bucks://` serves only the built-in app. For the registry, copy ENS conventions: store an EIP-1577 style `contenthash` as `bytes`, never `bytes32` as the draft contracts plan does, since a CIDv1 does not fit in 32 bytes ([EIP-1577](https://eips.ethereum.org/EIPS/eip-1577)). Resolution in the browser should never trust a single RPC: verify against a signed checkpoint plus a Merkle proof, or a light client where one exists. Helios does this for Ethereum and OP Stack in WebAssembly ([a16z](https://a16zcrypto.com/building-helios-ethereum-light-client/)); no browser light client for a Cosmos EVM chain was found, so a checkpoint-and-proof design is the safe assumption (inference).

Moderation and legal exposure need an explicit posture. A host that pins content is the party holding it. IPFS has a working stack: the compact denylist format and the NOpfs plugin for Kubo, with no list enabled by default ([IPFS blog](https://blog.ipfs.tech/2023-content-blocking-for-the-ipfs-stack/)), and Bad Bits is used by the public gateways ([IPFS docs](https://docs.ipfs.tech/concepts/public-utilities/)). Recommended default (inference, no legal research was done and counsel should review): ship a denylist enabled, host only user-chosen CIDs, and keep an abuse path for any Bucks-run gateway. Providers' IPs are visible to anyone who looks up an announced CID, so "browser as host" is a privacy trade-off to disclose.

## An agent that browses without becoming the attacker's tool

The Soul Engine already has good parts: a per-launch token, deny-on-timeout approval cards in the main process for browser actions, a quarantine for peer-supplied updates, and a provider fallback. It lacks the defences that the 2025 to 2026 browser-agent incidents show are required. Brave disclosed hidden-text, faint-image and navigation-triggered injections in Comet, Fellou and Opera Neon, and recommended isolating agentic from regular browsing and starting agent actions only on explicit user invocation ([Brave](https://brave.com/blog/unseeable-prompt-injections/)). OpenAI concedes injection is unlikely ever to be fully solved ([OpenAI](https://openai.com/index/hardening-atlas-against-prompt-injection)). Anthropic's own pilot measured a 23.6% attack success rate unmitigated and 11.2% with mitigations ([Anthropic](https://www.anthropic.com/news/claude-for-chrome)). Zenity reported a zero-click hijack of Comet in March 2026 (secondary summaries; primary reports were not read) ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-pleasefix-agentic-browser-exploits-2026032/)). Simon Willison's "lethal trifecta" (private data, untrusted content, external communication in one agent) says the only reliable mitigation is not combining them ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)), and Bucks' agent has all three. The current `safety.py` is regex keyword filtering with no injection or exfiltration logic; reframe it as content policy, not security.

The design below is my synthesis from Chrome's published architecture ([Google](https://blog.google/security/architecting-security-for-agentic/)) and the CaMeL paper, which keeps control flow in the trusted query and restricts data flow at tool calls, solving 77% of AgentDojo tasks with provable security versus 84% undefended ([arXiv 2503.18813](https://arxiv.org/abs/2503.18813)). First, a **separate agent profile** (its own session partition) with no access to the user's logged-in cookies unless the user grants a specific site. Second, a **trusted gate in the Electron main process**, not the Python LLM, that owns per-session read-only and read-write origin sets and denies any model-produced URL not already in the set. Third, a **planner/reader split**: the planner sees the user request and typed fields only; a quarantined, tool-less reader model summarises raw page text. Fourth, **capability classes** in place of the binary safe flag: read-page, read-private-store, write-local, network-egress, state-changing web action, publish/pin, spend/send, each with per-origin and per-session grants. Fifth, **IPFS publishing as a main-process tool** (`ipfs_publish_site`, `ipfs_pin`, `ipns_publish`) that always requires approval, with an approval card rendered by the trusted shell showing the real file list, size, destination name and key, never an engine-supplied label. Sixth, **no remote images or auto-links** in cards derived from untrusted text (the exfiltration channel the trifecta describes; the notes give the principle, not a verified incident). Seventh, a tamper-evident action log, rate limits and adversarial tests in CI. Peer messages (A2A-style agent cards signed by the Soul key and pinned in IPFS, per the inference in the agent note) must be treated as untrusted; A2A v1.0 shipped in 2026 under the Linux Foundation but has no libp2p binding, so any pubsub transport would be custom ([Linux Foundation](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)).

On protocols, expose the tool registry as an MCP server and gate third-party servers through a main-process gateway: MCP revision 2026-07-28 is stateless, makes authorization optional, and its security guidance requires showing the exact command before running a local server and blocking private-range URLs ([MCP spec changelog](https://modelcontextprotocol.io/specification/latest/changelog); [MCP security](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)). For local models, 8B-class Qwen models are the most consistent small tool-callers in the (mostly secondary) reports, with reliability falling below roughly 4B ([Docker evaluation](https://www.docker.com/blog/local-llm-tool-calling-a-practical-evaluation/)); small local models are probably easier to hijack than frontier ones (a hypothesis, no source), which is another reason defences must be architectural. Run Bucks' own evals on Bucks' own tool schemas. The notes did not research framework comparisons, passkeys, DoH, fingerprinting resistance, tab discarding, or which productivity features users value, so those sections of "efficient and productive" rest on inference: summarisation and local history search with tool-less output are lowest risk, multi-page research in the isolated profile is medium, and form-fill, messaging and purchases are high and must stay gated.

## The chain does not exist yet, so choose a base first

The Go node is roughly 2.2k lines and not a chain (chain note, Q1). The block header's RLP encoder returns an empty slice, so every block has the same hash; the difficulty retarget compares one block interval against a whole 2016-block window and so hits the clamp every time; `eth_getBalance`, `eth_getTransactionCount`, `eth_call` and `eth_sendRawTransaction` are constants; `bucks_getWork` returns the parent hash, so the miner and node do not agree on work; the mining flags never start a loop; the P2P identity key is regenerated each start; and the documented `state/` and `evm/` packages are absent. Both the node's RPC and the miner's local API send wildcard CORS and run unauthenticated, so a visited web page could rewrite the miner's payout address. The wallet extension uses PBKDF2 with 310,000 iterations (the architecture document says Argon2id; code wins), but ships a placeholder word list and cannot recover with the real one. Contracts (Solidity 0.8.24, six contracts, four test suites) have no deployment, no upgradeability and a single deployer key as admin by default. Separately, the browser wallet calls REST paths (`/api/address/*`, `/api/transactions/*`) that the Go node does not serve, and the REST server in the older line is deleted, so wallet and node do not currently match (audit G9; the chain note asks for confirmation). A second, larger C++ UTXO chain exists (about 49k lines, tested, SHA-256d PoW, no smart contracts); the project's own documents disagree about which engine is production-ready.

The notes compare launch paths (chain note, Q2 and Q3). I recommend, as inference from sourced facts, in this order. **Cosmos SDK with CometBFT and the Cosmos EVM module, scaffolded with Ignite**, for a Go team: it runs the existing Solidity unchanged, offers staking, governance and IBC precompiles, and gives sovereign parameters and one-block finality ([Cosmos EVM docs](https://docs.cosmos.network/evm/v0.5.0/documentation/evm-compatibility/overview)). Cautions: SDK v0.53.8 carries security fixes and is state-breaking ([release](https://newreleases.io/project/github/cosmos/cosmos-sdk/release/v0.53.8)); the newest Ignite is a release candidate (v30.0.0-rc.2); Cosmos EVM stubs some RPC methods; it is young. **An OP Stack rollup through a managed provider** is the fast alternative with Ethereum security and Helios browser verification, at the cost of a central sequencer, L1 data fees and unpublished RaaS prices. An **Avalanche L1** pays roughly 1.3 AVAX per validator per month (2024 to 2025 sources) ([Avalanche](https://academy.avax.network/guide/etna-changes)). Keeping **proof-of-work** only makes sense if a mined, gold-anchored coin is a hard requirement; a young PoW chain with no hashrate is cheap to attack, as the Monero hashrate episode of Aug 2025 illustrated for far larger networks ([Coin Metrics](https://coinmetrics.substack.com/p/state-of-the-network-issue-326)). Dropping PoW ends the miner product, which is why this is the owner's decision (D1). One more inference: with 60-second blocks and halving every 210,000 blocks, the first halving arrives after about 146 days, issuing about 75% of supply within roughly 1.2 years; revisit the monetary design before genesis.

For the platform that configures and operates the chain, build a thin control plane, `bucksctl` (CLI first, a web console later), not a SaaS. Its modules, all design: signed, versioned **network profiles** (devnet, testnet, mainnet with chain IDs, genesis hash, seeds, RPC list, contract addresses, minimum client version, and a verified checkpoint), published as a file and as an IPFS CID so the browser can fetch and check them; a **genesis builder** with schema validation (supply equals allocations, no fake faucet addresses, unique chain IDs, voting-power concentration warnings, a printed and pinned genesis hash, and a throwaway dry-run net with smoke tests); **provisioning and health** (configs and unit files generated from the profile, signed release manifests, alerts on height lag, missed blocks and disk); **key custody** (multisig deployer and admin behind a timelock, validator keys on a remote signer or KMS, offline release-signing key, a small hot faucet key, and no private keys in `.env` files); **faucet** (testnet only, rate-limited); an off-the-shelf **explorer** (Blockscout or Ping.pub-style) with a Bucks tab for names and storage deals; **RPC management** with origin allow-list, authentication for admin methods and body-size limits; a **contract pipeline** (pinned compiler, deterministic deployment, verification, ownership transfer to governance, bytecode hashes in the profile); an **upgrade flow** (halt-height binary upgrades rehearsed on a state export, proxy-plus-timelock contract upgrades); and **observability, backup and an audit log**. Metrics names, remote-signer tools and explorer products were not researched from primary sources, so treat those picks as options to verify.

Storage incentives should reuse proven designs. Filecoin's Proof of Data Possession, which uses randomised challenges verified by contract and pauses payments on failed proofs, went live on mainnet and is the closest working reference ([Filecoin](https://filecoin.io/blog/filecoin-onchain-cloud-is-live-on-mainnet), dated 26 Mar 2026). The network note instead says the launch was unconfirmed; the chain note's primary-vendor source resolves this in favour of "live", though launch dates differ across sources. Crust uses TEE-based proofs, Codex (now Logos Storage) paused its testnet, and no incentive network built for intermittently online laptops with audited economics was found. Proofs of possession are cheap on-chain; retrievability, latency and uptime are not, and are gameable by Sybil hosts proxying one copy. My recommendation: for the durable tier, pay a commercial pinning provider or integrate Filecoin's service rather than running a proof system first; add a custom-token reward for laptops only after the chain exists, tied to stake, per-ASN caps and bonded watcher probes.

## Roadmap, aligned with the Svelte removal

The consolidation plan makes Bucks-browser the single repository, freezes Bucks Core as a feature reference, and replaces Svelte with web components over 5 to 7 weeks for one developer (its own estimate), keeping the main process, the Soul Engine, the IPC contract and the Playwright tests (`docs/CONSOLIDATION-PLAN.md`). ## Conclusion

The goal of an `ipfs://`-first hosting infrastructure is technically sound and, on the evidence, closer on the browser side than on the chain side: the handler already gives per-CID origins, streaming and range support, and the missing pieces (site publishing, redirects, naming, pinning) are well-bounded main-process work. What changed during the research is where the risk sits. It is not in IPFS's protocol performance, which is good, but in who maintains the software and gateways around it, in the absence of any durability layer, and in a security posture that would let a prompt-injected agent publish publicly. Because those risks are cheap to reduce, the first two weeks of work are the highest-value of the whole roadmap.

Two points will surprise the owner. First, hosting every site by CID does not mean every site is hosted: without pinning, a Bucks-hosted site vanishes when a laptop sleeps, and no incentive network built for laptops exists to copy. Second, the chain platform is a greenfield build whose first output should be a base-chain decision and a devnet, not a console. Items still unknown and worth testing early: real-Electron origin and storage behaviour (blocked by disk space), public-network IPNS and retrieval latency (excluded by the safety rules of the experiment), what Kubo's `lowpower` profile does to providing, DNSLink label encoding in the subdomain proxy, and whether anyone takes over Kubo maintenance by the time Phase 1 ships.
