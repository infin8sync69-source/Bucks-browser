# Bucks Browser — Process Architecture & IPC Contract

This document is the single source of truth for how the three layers talk to each other.
`src/preload/preload.cjs` is the executable form of this contract. If you change one, change both.

```
┌──────────────────────────────────────────────────────────────────────────┐
│ Main process (src/main, ESM)                                              │
│  index.js ── wiring only                                                  │
│  ├ settings.js        JSON settings + bucks:settings:*                    │
│  ├ window.js          chrome BrowserWindow (frameless) + bucks:window:*   │
│  ├ tabs.js            TabManager: one WebContentsView per external tab    │
```

## Ownership of the tab model

* The **renderer** is the source of truth for the list of tabs, their order, which is active,
  bookmarks and history (persisted in localStorage, as today in `ui/src/lib/stores.ts`).
* The **main process** owns one `WebContentsView` per *external* tab (`http(s)://`, `ipfs://`,
  `ipns://`, `file://`). Internal tabs (`bucks://…`) have no view; the chrome hides the content
  area and renders a SvelteKit route instead.
* Tab ids are generated by the renderer and passed to main on `tabs.create(id, url)`.
* Views are created lazily: on startup the renderer only creates the view for the active external
  tab; other restored tabs get a view the first time they are activated.
* Back/forward for external tabs are Chromium's own history (`tabs.back/forward`). The renderer
  keeps its own back-stack only for internal routes.

## Content rectangle protocol

The chrome renders an empty placeholder element where the page should appear. A `ResizeObserver`
on it (plus a re-measure after any layout change, e.g. the chat drawer opening) calls
`bucks.tabs.setContentBounds({ x, y, width, height })` in CSS pixels relative to the window's
viewport. Main applies it to the active view with `view.setBounds`. While a full-screen overlay
(app store, modal widget, settings dropdown, omnibox suggestions) is open, the chrome calls
`bucks.tabs.setContentVisible(false)` and restores `true` on close.

Kubo download (first run, when no binary is bundled): `src/main/ipfs/dist.js` tries, in order,
`KUBO_DIST_URL` (env), `https://dist.ipfs.tech/kubo`, then GitHub releases
(`https://github.com/ipfs/kubo/releases/download/<v>/kubo_<v>_<os>-<arch>.tar.gz`). The small
`.sha512` is fetched first on each mirror, so a blocked mirror fails fast; every archive is verified
against the checksum from the same mirror, and a mirror without one is skipped (never installed
unverified). When every mirror fails, the error lists each mirror and its reason.
`scripts/fetch-kubo.mjs` uses the same mirror list.

## Security rules (non-negotiable)

* Chrome window: `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`, CSP meta in
  `ui/src/app.html` restricting scripts to `'self'` and connections to `'self'` + `http://127.0.0.1:*`.
* Web content views: `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`,
  `webSecurity: true`, no preload, partition `persist:bucks-web`.
* `ipfs://<cid>` is an origin per CID (scheme is registered `standard`). The protocol handler never
  serves anything from the chrome's files.
* `bucks://` is only ever served from `ui/build`; path traversal must be rejected.
* `setWindowOpenHandler` on every web contents returns `{ action: 'deny' }` and forwards the URL to
  the renderer via `bucks:tabs:open-request`.
* `will-navigate` / `will-redirect` to `bucks://` from web content is blocked and forwarded the same way.
* Permission requests (camera, mic, geolocation, notifications, midi, hid, usb, serial, bluetooth,
  clipboard-read) are denied by default for web content; `fullscreen`, `pointerLock`, `media` playback
  allowed. (A per-site allow list can come later.)
* Private keys never leave the renderer's wallet page; main only proxies already-signed transactions.

## Devices: pairing Bucks installs over IPFS peering + pubsub

Owner: `src/main/ipfs/devices.js` (Electron glue) and `src/main/ipfs/devices-core.js` (pure logic, no
Electron import, unit-tested). Wired in `src/main/index.js` as
`createDevices({ kubo, settings, userData, getMainWindow })`.

### Trust model

* A device is identified by its Kubo peer ID. Kubo signs every pubsub message (StrictSign), so the
  `from` field of a received message is authenticated.
* The user pairs devices explicitly on both machines. Paired devices live in
  `settings.ipfs.peers = [{ peerId, name, addrs }]`. Only messages from paired peer IDs can add
  shares. Presence from unpaired peers is shown as "discovered", never trusted.
* The topic is public: any node on the gossip mesh (not only the LAN) can read a device's presence
  (name, addrs, the CIDs it offered in the last 7 days) and may appear under `discovered`.
* `addrs` are multiaddrs **without** the `/p2p/<id>` suffix (that is how Kubo's `Peering.Peers` wants
  them). The UI and pair channel accept either form; devices.js strips the suffix.

### Kubo configuration (applied by kubo.js on every start, before the daemon runs)

* `Pubsub.Enabled = true`, `Pubsub.Router = "gossipsub"`.
* `Discovery.MDNS.Enabled = true` (LAN auto-discovery).
* `Peering.Peers = settings.ipfs.peers.map(p => ({ ID: p.peerId, Addrs: p.addrs }))` so paired
  devices stay connected and reconnect automatically. Entries are validated first: an invalid peer
  ID, our own ID or an unparsable multiaddr is dropped (Kubo refuses to start on one bad multiaddr
  in its config), a trailing `/p2p/<id>` is stripped, and with no valid entry `Peering.Peers` is `[]`.
* A daemon left running in our repo is only adopted when it reports `Pubsub.Enabled = true`;
  otherwise it is shut down and a correctly configured one is started.
* Only a change of `ipfs.mode`, or of `ipfs.externalApiUrl` while the mode is `external`, restarts
  the node. Changing `settings.ipfs.peers` or `settings.devices` must NOT restart it. devices.js
  applies pairing changes live with `swarm/peering/add|rm`, `swarm/connect` and
  `config Peering.Peers` — but only for changes made through `bucks:devices:pair|unpair` (and when
  a paired device advertises new addrs, and on every node start). Editing `ipfs.peers` through
  `bucks:settings:set` takes effect live only at the next node start, so the UI must use the
  devices channels.

### Pubsub protocol

Topic `bucks-devices-v1`. Kubo's HTTP API needs topics multibase-encoded:
`arg=u<base64url(topic) without padding>` → `uYnVja3MtZGV2aWNlcy12MQ`.
`pubsub/sub` streams NDJSON lines `{ from, data, seqno, topicIDs }` where `data` is `u` + base64url.
`pubsub/pub` takes the payload as a multipart file field. A node also receives its own messages:
drop any message whose `from` is our own peer ID. Messages published before the gossip mesh forms
are lost, so delivery relies on periodic re-announcement, not on single sends.

Payload (UTF-8 JSON, at most 16 KiB):

```json
{
  "v": 1,
  "type": "presence",
  "peerId": "12D3Koo…",            // must equal the message's `from`
  "name": "infin8sync-laptop",      // ≤ 64 chars
  "platform": "linux",              // process.platform
  "version": "2.0.0",               // app version
  "addrs": ["/ip4/192.168.1.20/tcp/40785"],   // ≤ 16, best first, no /p2p suffix (see below)
  "shares": [{ "cid": "bafy…", "name": "notes.txt", "size": 1234, "ts": 1792300000000 }],  // ≤ 20
  "ts": 1792300000000
}
```

* `addrs` excludes loopback, unspecified (`0.0.0.0`, `::`), link-local `fe80::`, `/p2p-circuit`
  and `/certhash/` addrs (webtransport / webrtc-direct certificate hashes rotate). They are ordered
  best first, because the UI shows `addrs[0]` as the pairing address and Kubo returns its addrs
  sorted as strings: LAN IPv4 (192.168/16, 10/8, 172.16/12), then 100.64/10, public IPv4, IPv6;
  TCP before UDP; an IPv4 ending in `.1` (a Docker / VM bridge the machine hosts) last.
* Presence is published right after subscribing, every 30 s, and immediately after pair, unpair,
  rename and share. Because messages sent before the gossip mesh forms are lost, it is also re-sent
  once ~4 s after subscribing or pairing, and when a paired device newly appears in `swarm/peers`.
* When a paired device's presence advertises a non-empty set of addrs different from the stored
  one, `settings.ipfs.peers[].addrs` (and the live peering) are replaced with it. An empty set
  never wipes the stored addrs.
* `shares` is the outbox: files this device offered to its paired devices in the last 7 days, newest
  first. Re-sending the outbox in every presence gives eventual delivery despite lost messages.
* Receivers validate everything (types, lengths, CID parses, addrs start with `/`) and ignore
  invalid messages. They dedupe shares on `(from, cid)`.
* A paired device is `online` when its presence arrived in the last 90 s, and `connected` when it is
  in `swarm/peers`.

### Persistence

`<userData>/devices.json` stores `{ outbox: [...], received: [...], seen: [...] }` (received keeps
at most 100, newest first; `seen` holds the `(from, cid, ts)` keys of every share already received,
kept 8 days, at most 500, so dismissed or evicted shares are not re-added from the sender's
re-announced outbox; a share re-offered with a newer `ts` is accepted again). The file is written
atomically; a corrupt file is logged and replaced by empty lists. Pairings live in settings.

```ts
  error: string | null;           // e.g. 'Pubsub is disabled on the external IPFS node. Set Pubsub.Enabled…'
  topic: 'bucks-devices-v1';
  self: { peerId: string | null; name: string; platform: string; version: string; addrs: string[] };
  paired: Array<{ peerId: string; name: string; platform: string | null; version: string | null;
                  online: boolean; connected: boolean; lastSeen: number | null; addrs: string[] }>;
  discovered: Array<{ peerId: string; name: string; platform: string; version: string;
                      lastSeen: number; addrs: string[] }>;   // unpaired presence seen in the last 5 min
  received: Array<{ cid: string; name: string; size: number | null; from: string; fromName: string;
                    ts: number; pinned: boolean }>;
}
```

### Channels

| Channel | Payload → Result |
|---|---|
| `bucks:devices:status` | → `DevicesStatus` |
| `bucks:devices:pair` | `{ peerId, name?, addrs? }` → `DevicesStatus`. `peerId` may also be a full multiaddr ending in `/p2p/<id>`. |
| `bucks:devices:unpair` | `{ peerId }` → `DevicesStatus` |
| `bucks:devices:rename` | `{ name }` → `DevicesStatus` |
| `bucks:devices:share` | `{ cid, name?, size? }` → `{ queued: true, onlinePeers: number }` |
| `bucks:devices:dismiss` | `{ cid, from }` → `DevicesStatus` |
| event `bucks:devices:updated` | `(DevicesStatus)` on any change (presence, pairing, share, ready state) |

When `settings.devices.autoPin` is true, shares from paired devices are pinned on arrival
(`pinned: true` once `pin/add` succeeds). Otherwise the user pins from the UI with `bucks.ipfs.pinAdd`.
